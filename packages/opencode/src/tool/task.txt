Delegate work to a subagent: an independent agent session with its own context, tools,
permissions, and conversation history. The subagent works autonomously and returns a
final result to you.

## PARALLEL DISPATCH IS THE DEFAULT FOR INDEPENDENT WORK

If a task contains two or more independent questions, files, investigations, or test
areas, make multiple Task tool calls in the SAME assistant message. Those calls run in
parallel. Do not call one agent, wait for it, and then call another when the second
does not depend on the first result.

Good parallel fan-out:
- Agent 1: inspect the API and identify relevant routes.
- Agent 2: inspect the tests and report missing coverage.
- Agent 3: inspect the UI and report rendering or interaction impact.

Bad serial dispatch:
- Call an agent to inspect the API.
- Wait for its result.
- Call another agent to inspect unrelated tests.

Use parallel agents freely for read-only exploration, search, auditing, triage,
summarization, and independent test analysis. For write tasks, partition ownership
before dispatching: never have two agents edit the same file or overlapping code at
the same time. If work is dependent, dispatch the prerequisite first, then use its
result in a follow-up call.

Every parallel call must still be a complete, standalone task. Give each agent a
non-overlapping scope and tell it exactly what to return. Do not duplicate work that
has already been delegated.

## Select the subagent

You MUST provide `subagent_type`. Choose the available specialist whose description
best matches the work. The tool description lists the allowed agent types and their
capabilities.

Use a short `description` (3-5 words), and write a self-contained `prompt`. The
subagent cannot see this conversation unless you explicitly include the relevant
context. State all of the following in the prompt:
- the concrete goal and scope;
- the files, symbols, or subsystem it owns;
- whether it should investigate only or modify files;
- constraints and non-goals;
- the verification command or test it should run;
- the exact format and evidence required in its final response.

Ask the subagent to return a concise summary of findings, changes, failures, and
next steps. Its result is returned to you, not directly to the user. Relay the useful
result in your response to the user.

## When to use this tool

Use Task for work that benefits from context isolation, specialist expertise, or
parallel execution. Examples include repository exploration, code audits, debugging,
test investigation, independent implementation slices, and focused research.

Do not use Task for a tiny operation you can complete immediately yourself:
- reading one known file: use Read;
- locating a symbol or exact text: use Grep or Glob;
- inspecting a small two- or three-file change: use the direct tools;
- work for which no available agent is suitable.

The gain is isolated context and concurrency, not a license to delegate every small
operation.

## Fresh work versus resuming work

Omit `task_id` to start a new subagent with a fresh context. Include `task_id` only
when continuing that exact subagent session after a result, failure, cancellation, or
request for more work. Resuming preserves the subagent's existing context; do not
restate the original task as if it were a new investigation.

If a subagent fails or is cancelled, do not silently restart from scratch. Use the
reported `task_id` to resume the preserved session, or inspect that session's
messages first. Start a fresh subagent only when the original approach was wrong.

## After dispatch

For foreground work, wait when you need the result before taking the next dependent
step. For multiple independent foreground calls, issue them together and wait for
all of their results before synthesizing a conclusion.

Never duplicate a delegated task, poll it by repeatedly launching the same task, or
ask a second agent to touch the same files while the first is working. Continue with
non-overlapping work only.
