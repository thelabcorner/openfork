# V1 vs V2/current

“V1” and “V2” are overloaded terms in this repository. Treat them as separate axes.

OpenFork deliberately chooses different generations on different axes:

```text
presentation/UI       -> V2/new-layout is the forward product direction
execution/runtime     -> V1 is the mature production target
local client/API      -> V1/fork contract is the target
current/V2 runtime    -> semantic/reference + selective backport source
```

## Axis 1: execution/domain generation

This is the architectural distinction that matters most.

| | Legacy / V1 | Current / V2 |
| --- | --- | --- |
| Primary runtime owner | `packages/opencode` | `packages/core` |
| Session execution | `src/session/prompt.ts`, `processor.ts`, related V1 session modules | `src/session/runner/*`, `execution/*`, input/event/projector services |
| Tool registry | `packages/opencode/src/tool/registry.ts` and V1 tool tree | `packages/core/src/tool/registry.ts`, `builtins.ts`, current tool services |
| Persistence model | legacy-compatible session/message structures plus shared Core persistence seams | durable Core domain rows/events, admitted session input, projectors |
| Architectural role in OpenFork | active mature production path; repair, extension, and backport target | current domain model; semantic/reference architecture and backport source |

V1 is still production code. More importantly, **OpenFork does not inherit
upstream's V1-retirement policy**. Upstream is moving consumers from the legacy/V1
architecture toward current/V2. OpenFork intentionally has a different lifecycle
goal: keep V1 healthy, repair its architectural weaknesses, and selectively
backport current/V2 semantics and features into V1 where they improve the mature
runtime.

Current/V2 being the architectural or behavioral reference therefore does **not**
mean it is automatically the destination runtime for OpenFork. It means its
semantics can be used as evidence for how a capability should behave, then placed
at the correct shared owner and adapted into V1 without preserving legacy
heuristics.

Examples of semantics that must converge across generations include:

- turn provenance and ownership;
- instruction authority vs provider role;
- Goal lifecycle and continuation behavior;
- session/tool lifecycle state;
- event and projection semantics;
- shared provider/tool protocol behavior where applicable.

## Upstream migration vs OpenFork backport policy

| Question | Upstream direction | OpenFork direction |
| --- | --- | --- |
| V1 lifecycle | Legacy/transitional path that upstream is moving away from | Supported production path; repair and extend it unless OpenFork explicitly decides otherwise |
| Current/V2 runtime role | Replacement/current architecture | Reference architecture and backport source; not OpenFork's product destination |
| Current/V2 local client API role | Migration target | Not a product compatibility target; retain only where currently required or deliberately useful |
| V2/new-layout UI role | Newer presentation generation | **Primary OpenFork presentation direction; continue developing it** |
| Typical feature movement | Move callers/behavior from V1 toward current/V2 | Prefer the lowest shared owner; backport suitable current/V2 behavior into V1 |
| V1 deletion | Natural consequence once upstream migration completes | Requires an explicit OpenFork architecture decision; never follows from an upstream rename or migration alone |

This is not a license to copy V2 implementation files wholesale into V1. Backport
the **semantic capability at its authoritative owner**. If a provider rule belongs
in `packages/llm`, a durable concept belongs in Core/Schema, or an HTTP contract
belongs in a shared API layer, fix it there and make both generations consume it.
V1-specific adapters should exist only where the mature V1 execution model actually
needs adaptation.

## Axis 2: HTTP/API generation

API naming does **not** map cleanly onto runtime generation.

`packages/app/V1_API_MIGRATION.md` is an **historical upstream-direction ledger,
not the OpenFork roadmap**. It defines its “V1 API” as the legacy unprefixed HTTP
endpoints, even though many of those calls are exposed through a package named
`@opencode-ai/sdk/v2`.

Practical rule:

- V1 local client/runtime behavior is the OpenFork product target;
- current Protocol endpoints live under the upstream-current `/api/*` contracts,
  but OpenFork does **not** need to complete or preserve that API family for its
  own sake;
- the full `OpenCodeHttpApi` composes both current Protocol APIs and OpenCode-owned
  local runtime routes today because the tree is hybrid;
- `@opencode-ai/sdk/v2` is a generated-client namespace, **not proof that a call is
  using the current/V2 execution runtime**;
- an existing `/api/*` consumer may remain while it is useful, but new work should
  not migrate V1 callers to current client APIs merely to follow upstream.

### What “write off the current client API” means

It means **no OpenFork compatibility obligation**, not blind deletion:

1. do not spend engineering effort completing upstream's V1 -> current client API
   migration solely for version convergence;
2. do not treat Protocol/client parity as a release criterion for OpenFork;
3. do not remove V1 local contracts because a current endpoint exists;
4. when a current endpoint already serves a fork feature well, it may stay as an
   implementation seam until a deliberate simplification is worthwhile;
5. when backporting a V2 feature, port the semantic capability into the V1-oriented
   architecture rather than importing its client API dependency by default.

This section concerns the **OpenFork local client/server API only**. The hosted
OpenCode model gateway (Zen/Go, currently versioned independently) is external
provider infrastructure and must remain compatible through the provider layer.

More generally, no local V1/current API choice creates a promise that OpenFork is
drop-in compatible with OpenCode clients, plugins, or extensions. OpenFork owns both
sides of its local contract and may evolve them together.

## Axis 3: UI generation

Folders and components named `v2` under `packages/app` or `packages/session-ui`
usually identify the newer presentation/component generation. **Unlike the
current/V2 runtime and current client API, this UI generation is not merely a donor
surface: it is the preferred OpenFork product UI.**

Examples:

- `packages/app/src/pages/session/v2/*`
- `packages/app/src/components/settings-v2/*`
- `packages/session-ui/src/v2/*`

Current code makes that direction concrete:

- `newLayoutDesignsDefault = true`;
- the legacy-interface sunset is September 14, 2026 and retired state forces
  `newLayoutDesigns()` true;
- the primary desktop/web shell is `NewAppLayout` / `NewLayout`;
- the primary settings route loads `settings-v2/settings-screen`;
- the session path uses V2/new-layout prompt input, project explorer, terminal,
  file/review presentation, browser panels, and newer timeline actions.

This does **not** couple UI generation to the other axes. These names do not by
themselves answer:

- which HTTP endpoint is called;
- which generated client is used;
- whether execution runs through V1 or Core/current;
- who owns the underlying domain state.

The root `AGENTS.md` states this directly: a “V2” suffix in a UI component is not an
API-version decision.

Practical rule: prefer the V2/new-layout presentation when building product UI, but
connect it to the authoritative OpenFork domain/runtime contract regardless of
whether that contract is V1, shared, or a deliberately retained current endpoint.

## Hybrid seams

The important shared/transition seams are:

- `packages/opencode/src/server/routes/instance/httpapi/*` — one full local API host;
- `packages/opencode/src/session/message-v2.ts` — an internal V1/current bridge
  inside the legacy host package;
- `packages/core/src/v1/*` — centralized V1 internal-compatibility logic that belongs in
  Core rather than being reimplemented by every consumer;
- `packages/app/src/context/server-sdk.tsx` — client-side V1/current bridge
  transport composition;
- `packages/schema` — browser-safe shared contracts;
- `packages/llm` — provider wire/protocol behavior shared below execution hosts.

## Direction of travel

```text
        current/V2 runtime semantics
                    |
              inspect and prove
                    v
        lowest shared semantic owner
                    |
                    v
        repaired OpenFork V1 runtime/API
                    |
                    v
          V2/new-layout presentation
```

New cross-generation behavior should normally be designed in the lowest shared
semantic owner first, then adapted into V1 where needed. When upstream implements
an improvement only in current/V2, treat it as a candidate for semantic backport,
not as evidence that OpenFork should abandon the corresponding V1 path or migrate
its client calls to the current API. The UI may still use or extend the V2/new-layout
presentation for that feature. Avoid creating a third presentation generation or a
one-off route-specific semantic implementation.

## Review checklist

When you encounter “V1” or “V2”, identify which axis is meant:

1. execution/domain runtime;
2. HTTP/API surface;
3. generated-client namespace;
4. UI component generation;
5. schema/message compatibility.

If a design argument relies only on a `v2` pathname or SDK import suffix, it has not
established the architectural boundary.
