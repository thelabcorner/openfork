# Completion review: remaining discriminators

Reviewed October 1, 2026 against the current main investigation ledger, installed `build-excerpts.json`, and the control-priority audit. The ledger already covers the user's architecture scope, evidence qualifications, V1 boundary, transport/server/storage/worker/rendering owners, autonomous repair, and 1/3/6+ Electron closure. Installed excerpts specifically establish that repair retries and activation repair shipped, along with the serialized interest POST and its `interactive`/`background` classification. The ledger correctly leaves the active tab-switch symptom unproven and does not blame missing repair code.

Two concrete items would make the proposal and next investigation more discriminating:

1. **Define cancellation's completion contract.** The three workload classes include cancellation, and the plan requires bounded cancel-to-observed-stop time, but it does not define the linearization point or response semantics. Specify when cancellation is merely accepted versus when it is complete; name the authoritative execution owner/generation that fences further provider/tool starts and content publication; and define behavior for a currently uninterruptible tool. Test that a cancel accepted during a blocked provider/tool call prevents later work and that no stale-generation completion can publish after stop. This prevents a fast HTTP acknowledgement from being mistaken for actual cancellation.

2. **Use a paired catalog-path experiment to test the startup-switch hypothesis.** The installed excerpt proves V1 startup selects `/api/agent`; the ledger also establishes that the prior V1 agent route crossed instance middleware. Therefore route name and graph breadth alone do not show that the switch caused extra latency. In an isolated instrumented sidecar with a fixed directory, compare the current `/api/agent` path and the retained V1 agent path under identical cold and warm conditions. Record request queue, connection wait, route entry/exit, location graph acquisition/compile, config/plugin/tool-reload stages, DB and event-loop delay, response, and created-instance count. Repeat with plugin/tool initialization deliberately blocked. If both paths initialize the same graph and stall equally, the switch is not the causal regression; if only the current path pays additional stages, those spans identify the attributable delta. Do not use the live user's workspace for this experiment.

The larger unresolved experiment remains a selected, actively streaming Electron session with correlated activation generation, interest POST enqueue/start/response, server registry mutation, SSE sequence/cursor, repair request, and first visible content. The installed window snapshot had no mounted timeline rows, so it cannot settle whether the shipped interest race explains the reported tab-switch symptom. The ledger already requires this active-load trace for closure; this review adds no claim that it has been captured.

## October 2 resolution note

The first discriminator above is now materially implemented for the V1 control path. Generation-CAS cancellation that is superseded returns false rather than "accepted"; the compatibility adapter propagates that result; local `SessionRunState.stopCurrent` supplies its exact registered generation when requesting the durable interrupt; and rollback/revert no longer suppresses an interrupt failure before mutating session state. Focused HTTP, RunState and app compatibility regressions are green.

The larger active-load experiment has also advanced beyond the October 1 state: the native Electron sidecar gate now exercises production desktop admission/urgent transport at 1/3/6 concurrency with a real sidecar, one live SSE reader and visible Markdown tails, while the renderer gate separately proves multi-block history reuse and fenced Shiki work on the reserved tail lane. See the main investigation, transport ledger and renderer ledger for current scope and remaining qualifications.
