# Session activation and control-priority audit

Date: October 1, 2026. Scope: read-only source audit of the renderer request scheduler, stream-interest control, session cache activation/repair, and server event delivery. This is a companion to `docs/perf/2026-10-01-performance-regression-investigation.md`; it does not replace the evidence ledger or claim live runtime reproduction.

## Verdict

There is a confirmed client-side priority gap and a confirmed ordering race between local timeline activation and server-side stream interest. The UI marks a session active synchronously, but the remote interest POST is asynchronous and is not awaited as an activation prerequisite. While one POST is queued or in flight, later desired interest sets are suppressed until its promise settles. A prior request can therefore continue to govern server filtering while the user has already activated another session. When the queued request is visible/nonempty it is only `interactive`, which cannot use the scheduler's critical reserve; clearing interest is `background`.

This is sufficient to explain delayed or missing live content during congestion, followed by catch-up on repair/hydration, but it does not prove that this race caused a particular installed-build symptom. The main performance ledger establishes a separate measured delay: 80.3 seconds of stream-interest scheduler wait in the installed build, then at most 298 ms of service time. Its deterministic scheduler reproduction shows visible interest waiting behind four interactive tasks while a critical prompt admission passes. Do not conflate those results with a live reproduction of stale server filtering.

## Authoritative path and demand path

The execution/message producer is V1 session runtime; it emits lifecycle and content events. The server global event route subscribes to the global bus, applies interest filtering, coalesces and places live events in a bounded subscriber queue, then emits SSE. The client stream starts with interest headers, while a separate POST updates the in-memory server registry. `ServerSession` owns local activation, stale/suspended state, message reconciliation and stream-repair retries. Timeline activation calls `resume` and sync/repair; the event reader consults the store before queueing content; the timeline renders the resulting cache.

Reverse demand: the visible timeline needs content for session S. `resume(S)` immediately adds S to local `activated` and synchronously publishes the desired set, but the callback only enqueues a remote POST. The SSE stream may still filter against an older set until the POST reaches and mutates the server registry. A stale marker or dropped local delta makes the session cache stale; repair fetches authoritative message pages and gates subsequent deltas during reconciliation. This recovery is useful but does not establish a bounded activation or first-content time.

## Verified mechanisms

### Renderer scheduler

`packages/app/src/utils/server-request-scheduler.ts:1-20,45-59,145-172,175-190,280-298` defines `critical`, `interactive`, and `background`, reserves capacity for critical jobs, limits background concurrency, and can promote queued entries by key. It is a finite-request admission gate only; its own comments exclude the long-lived SSE stream. Once work is admitted, it cannot preempt it.

`packages/app/src/context/server-sdk.tsx:797-810` constructs it at concurrency 5 with background concurrency 2 (default critical reserve 1). `streamInterestUpdatePriority` at `:720-722` maps nonempty visible interest to `interactive` and empty interest to `background`. The ledger's deterministic fixture holds four interactive slots, queues visible interest as interactive, then confirms a critical job starts before interest.

### Latest-interest race and missing activation barrier

`packages/app/src/context/server-sdk.tsx:827-887` returns immediately when `remoteInterestQueued` or `remoteInterestInflight` is set. It captures `key` and `sessions` before scheduling the POST (`:834-854`), checks the JSON `{updated:true}` response before recording `remoteInterestAck` (`:856-870`), and only submits a newer set from `finally` after the existing promise settles (`:883-885`). The scheduler key is attached for promotion (`:871`), but this call site does not call `requests.promote`. `setStreamContentSessions` publishes the local set and calls `queueRemoteInterest` (`:890-905`); it does not return/await an acknowledgement.

`packages/app/src/context/server-session.ts:1232-1244` makes `resume(sessionID)` synchronous: it activates locally, clears suspension unless stale, and publishes interest. `sync` invokes `resume` before its network work (`:1125-1147`). `packages/app/src/context/server-sync.tsx:410-435` wires that callback to the SDK and wires the local content gate/invalidator. Therefore there is no end-to-end “server now admits content for this activation” boundary. `remoteInterestAck` is bookkeeping only; no activation caller waits on it or rejects readiness while it is behind.

Concrete race: server currently admits `{A}`; local navigation switches to B and queues `{B}`. Before that POST is admitted/acknowledged, activation changes again to `{C}`. Because `remoteInterestInflight` is set, `{C}` cannot replace `{B}`. Server may filter B/C content using A until the captured B request settles and a second request carries C. An in-flight request is not preemptible by the scheduler, and queued work is not promoted here. The same ordering applies when a visible set is queued behind other interactive work. Hidden visibility intentionally advertises `[]` (`server-sdk.tsx:716-722,1327-1340`), so restore adds another asynchronous transition.

Counterexample/limit: if the previous interest request has already completed and the server registry update is fast, this race window may be negligible. When the stream is not interest-aware (or an old server returns unsupported), the server's initial-header/compatibility behavior differs; the client marks the feature unsupported (`:856-866`). The race is established in current source, not in the September 30 installed artifact.

### Local reconciliation and autonomous repair

`packages/app/src/context/server-session.ts:300-319` tracks activated, suspended and stale sessions plus stale generations. `sync` promotes same-session queued requests and waits for in-flight sync before forcing a current page when stale (`:1150-1163`); repair installs reconciliation state before it admits new deltas (`:1187-1190`). `acceptStreamContent` gates deltas for inactive/stale sessions and records cached sessions as stale (`:1246-1267`). An active stale session retries repair with bounded exponential backoff while still active (`:1269-1315`). Prefetch is serialized separately and foreground work bypasses its tail (`:1328-1360`).

These are good local convergence defenses. The parent audit has since verified from `build-excerpts.json` that the September 30 installed build already contains the autonomous retry and timeline-activation repair behavior. Therefore the tab-switch symptom must not be attributed to absence of those repairs. They do not repair the interest-control acknowledgement gap: a repair can begin while server delivery still follows stale interest, and a retry loop can keep paying for pages while a control update is stuck behind a slow admitted request. The callback also lacks a generation token with which to reject an old acknowledgement after a newer activation.

### Server registry, queues and event-loop boundary

`packages/server/src/event-interest.ts:57-92` stores one process-local interest record by subscriber ID; `updateEventStreamInterest` replaces the set synchronously and returns false for an absent subscriber. It clears suppression latches for newly admitted sessions. `packages/opencode/src/server/routes/instance/httpapi/handlers/global.ts:673-677` returns that boolean as `{updated}`. This is an acknowledgement that the registry write occurred, not an acknowledgement that the SSE reader has observed a sequence/cursor boundary or that content for the newly admitted set is deliverable.

The global event route registers interest while constructing the stream (`global.ts:324-350`), then captures/replays, filters, coalesces, and offers frames (`:365-425`, with replay handling later in the function). Interest-suppressed frames turn into progress/stale control events (`:386-418`). The native route has the corresponding pattern in `packages/server/src/handlers/event.ts:142-247,299-325`. In both cases, live content and stale/progress frames ultimately use the same bounded subscriber FIFO; event coalescing and replay ordering can delay live content, and the queue does not provide a dedicated control lane.

The separate interest handler is a lightweight registry write and does not itself demonstrate a SQLite wait. However, it still shares HTTP ingress, process scheduling, and the event loop with other server work. A synchronous native SQLite call, long event-loop task, saturated transport/socket, or SSE backlog cannot be bypassed merely because the renderer assigned a priority. No source evidence here proves which of those was responsible for the 80.3 second observed queue wait; that wait was recorded in the renderer before service began.

## End-to-end contract to implement

Keep V1 session execution and local API semantics. Make activation a control operation with one authoritative desired-state owner and an explicit server barrier:

1. The timeline activation owner issues a monotonically increasing activation/interest generation and immediately records the desired session set. One shared controller coalesces pending sets to the latest generation; it must not retain an obsolete captured set behind an in-flight request. Deactivation/empty-interest updates have the same control priority as activation because they release server work.
2. Transport gives control work a reserved finite-request lane (or separate connection budget) that ordinary interactive catalog/read jobs cannot occupy. Avoid relying on priority labels alone when the same HTTP/1 connection pool can be held by long requests. Queued stale generations may be replaced; in-flight HTTP cannot be assumed cancellable, so server application must be latest-generation-wins.
3. The existing fork-owned interest endpoint (or a narrowly versioned extension of it) accepts subscriber ID, generation, desired sessions and last observed stream cursor. Server validates subscriber ownership, ignores older generations, atomically installs the new set and returns `{generation, applied, cursor}`. Keep current V1 API usage; this is not a migration to Protocol/current `/api/*`.
4. Readiness for visible content requires both the server acknowledgement at generation G and a reconciliation boundary: replay/snapshot through cursor C, then live events after C. Acknowledgement must be sequenced with SSE registration/replay so there is no gap between “applied” and “content begins.” If adding an ack event to the existing SSE route is narrower, use it; do not create a second raw content stream.
5. Server owns filtering and compact stale/progress projection. Control acknowledgements/stale markers must not sit behind bulk content bytes in a FIFO. Keep bounded memory and preserve per-session sequence ordering; control priority cannot reorder data past the cursor it acknowledges.
6. `ServerSession` remains the owner of cache reconciliation. It accepts content only for the acknowledged activation generation after snapshot reconciliation starts, discards stale-generation responses, and retries a failed repair while the same activation remains desired. One newer activation supersedes obsolete repair/network work. Suspension/deactivation closes that generation and releases its demand.

The scalable flow is: V1 producer/storage -> V1 event owner -> global event/SSE and interest registry -> client activation controller -> ServerSession snapshot/delta reconciliation -> timeline. The reverse demand is a user-visible activation generation flowing back to the server registry and returning an applied generation/cursor before rendering depends on the stream. Each layer owns its state once; no catalog scheduler, history hydration, or stale repair loop substitutes for that barrier.

## Negative tests and verification contract

- Hold every noncritical renderer slot with blocked catalog reads; activation, interest update, deactivation, cancellation and control acknowledgement still make bounded progress. Assert ordinary requests cannot occupy the control reserve.
- Block an older interest POST, change desired sets repeatedly, and verify only latest desired generation is applied after the blocked request releases; no obsolete captured set can become final. Verify explicit cancellation/timeout does not leave the local generation waiting forever.
- Delay/stall the server's unrelated catalog/index/maintenance work and verify the interest registry update plus V1 prompt admission/control operation progresses. Assert Tier 0/control path creates zero workspace instances and performs zero database work where the operation is only subscriber registry state.
- Race activation with SSE reconnect, replay, hidden/visible transitions and stream drops. Assert acknowledged cursor C plus reconciliation yields every required delta exactly once or an explicit repair, with no event gap and no stale-generation delta reaching the timeline.
- Fill the live subscriber content queue with large frames; prove acknowledgement, stale marker, cancellation and teardown remain deliverable while respecting byte bounds and per-session sequence constraints.
- Keep a mounted active timeline through failed repair attempts and prove it converges without tab switch/focus/remount. Deactivate mid-repair and prove the loop/request is cancelled or made inert.
- Run Electron + sidecar scenarios at 1, 3, and 6+ simultaneously working sessions; report activation-to-server-ack, ack-to-first-content, content age, queue wait/service, event-loop delay, DB wait, event bytes, renderer queue age and repair count. Repeat with deliberate unrelated background stalls. Idle startup and isolated scheduler unit tests are not closure.
- Negative invariants: zero N-per-session interest requests/streams, zero stale-generation delivery, bounded latest-state queue cardinality, no content-only hydration for list metadata, no implicit workspace instance on control path, bounded repair attempts/concurrency, and convergent teardown.
