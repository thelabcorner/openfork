# Renderer, timeline, and Markdown audit

Date: October 1, 2026. Scope: read-only source and retained investigation evidence. This is an architecture audit, not a performance closeout. No app/server restart, UI/session mutation, or production source edit was performed. `C:\DEV_STORAGE_GUIDE.md` and `C:\DEV_STORAGE_MAP.json` were absent, as recorded in the main ledger.

## Findings

### Dense working indicators: the historical hot path is materially improved

The September 28 fan-out report measured compositor Layerize cost during working-row animation. Each spinner had 16 rectangles total, 12 animated; the two sidebar copies of a working session therefore produced 24 animated rectangles per session. Its A/B established that merely pausing the SVG animations did not remove the layerization cost. The report also found one shared clock still caused off-screen row repaint/tooltip attribute mutations each second. These are historical measured causes, not proof of today's current cost.

Current source provides `DenseWorkingIndicator` as one HTML span with a single pulse class in `packages/ui/src/components/spinner.tsx:55-71`; repeated row call sites use it in `packages/app/src/pages/layout/sidebar-items.tsx:69,128` and `packages/app/src/pages/session/v2/chat-sidebar-pane.tsx:2282`. The larger SVG `Spinner` remains available at lines 14-51 for non-dense surfaces. This addresses the repeated 16-rectangle spinner mechanism. It does not alone bound total animations: expanded and Recent listings can still duplicate a session, and animated CSS work may remain for mounted offscreen rows. The older report's duplicate rows and shared-clock findings therefore remain validation concerns, not confirmed present-day regressions.

### Markdown has two CPU lanes, but three kinds of work share each lane

`packages/session-ui/src/components/markdown-worker.ts:45-48` declares two workers. Stable FNV affinity in `:119-128` pins a key to one worker. Parse, project, and highlight transports each use the same lane configuration (`:153-212`), with one active request per lane. This prevents one parse transport from stuffing multiple jobs into a serial worker and distributes unrelated keys across two workers.

However, `markdown.worker.ts:44-67` constructs separate latest-job queues for highlight, project, and parse in each worker. The single `self.onmessage` handler (`:89-105`) feeds those queues independently, and each queue can schedule its own asynchronous runner. Those queues are not CPU reservations. Parse can invoke asynchronous code highlighting (`:75-86`, `:108-155`), while project/highlight work and their queued dispatches run in the same worker event loop. A key's live markdown, code highlight, and projection are deliberately affinity-co-located, so an expensive parse or language load can delay that key's other markdown work; enough same-lane distinct keys can also build pending work. Main-side supersession and bounded queues limit waste, but the worker's 4 ms yield in `markdown-worker-queue.ts:38-79` cannot interrupt a synchronous lexer or Shiki operation already in progress.

The 2-lane design is a useful head-of-line reduction, not an end-to-end foreground priority guarantee. The visible tail, hidden mounted Markdown components, completed-history parsing, and code highlight currently have no explicit visibility/foreground class in this transport contract. Distinct transport instances also each admit per-lane work; their independent `maxActive` values do not add up to one shared per-worker reservation. Worker traces already record dispatch wait, response wait, queue wait, duration, and kind in `markdown-worker.ts:81-112`, but trace activation is opt-in (`markdown-trace.ts`). Thus the ledger's zero trace counters cannot establish actual current contention or its absence.

### Rendering reduces suffix churn, while parse results can still race pacing

The Markdown component projects blocks, reuses stable prefixes, skips unchanged block objects, and only updates changed DOM blocks (`packages/session-ui/src/components/markdown.tsx`, render resource and effect; `pendingBlocks` and `updateBlock` below the component). On streamed text, unchanged historical blocks are intended to remain inert. Worker parse/project state has byte/key caps (`markdown.worker.ts:23-42,54-87`), and main cache budgets exist in `markdown.tsx` and `markdown-cache.tsx`.

Those mechanisms bound/reduce work but do not prove display cadence. The component's asynchronous `Promise.all` for changed suffix blocks waits for parse/highlight results before the completed result is applied; while pending, it uses a fallback projection, which may be refreshed as upstream text changes. A fast stream can supersede parses; a slow final parse can leave the visible tail on fallback until it resolves. The needed guarantee is latest-state display by a frame/deadline, with stale results discarded, not that every provider fragment receives a full parse. Current source preserves the no-whole-history-on-each-token direction, but actual time-to-visible-content under occupied workers remains unmeasured.

### Timeline is virtualized and structurally projected; update cost still scales with history

The authoritative renderer path is durable/session message state -> sync store -> timeline projection -> row model/reconciliation -> virtualized rows -> SessionTurn/Markdown. `packages/app/src/pages/session/timeline/message-timeline.tsx:306-328` reads the selected session messages and derives projected messages; virtualizer setup is at `:545`, and virtual item memoization at `:657`. `projection.ts:101-128` rebuilds message lookup/assistant-parent structures from the supplied message array; `:151-196` documents and builds stable grouped turn/view structures, while later row-index memos supply O(1) keyed lookups. Row reconciliation and stable references reduce DOM churn, but an update that replaces/reconciles the full message array can still make the source-array maps/grouping scale with loaded history. Virtualization limits mounted DOM; it does not make history projection O(1).

The component-level `SessionTurn` likewise uses `props.messages` or the store's session messages (`packages/session-ui/src/components/session-turn.tsx:184-236`) and derives assistant/turn properties from those collections (`:274-440`). Dense navigation should continue to receive materialized scalar projections; it must not call these detail/history paths for badges. Existing sidebar hover/search prefetch is explicit user-intent warming, not decoration (`packages/app/src/pages/session/v2/chat-sidebar-pane.tsx:870-878`, `:2166-2206`). The September 28 report says the provider-specific history reconstruction was later removed (its F3 section, lines 248-266); that is a statement in the historical report, not independently verified current source or runtime evidence in this audit. The original scan/remount was measured at that capture. Keep its negative invariant in regression gates, and treat present-day absence/closure as unverified.

### Hidden UI must stop optional rendering, never required execution

The root and package contracts say keep-mounted hidden tabs/panels must not retain provider queries, history hydration, per-row timers, or data-only subscriptions. The reviewed timeline and Markdown paths expose no end-to-end visibility priority in the worker request type/transport above. A component may be unmounted or retained by its host, and this static audit does not establish which hidden tab instances are mounted in the current runtime. Treat hidden Markdown parse/highlight and timeline DOM work as an unresolved risk until an actual tab/visibility trace identifies their request volume. Required provider/tool execution and persistence for sessions in other tabs must continue; visibility should gate optional projection/rendering only.

## Ownership path and proposal

Producer/storage owns durable messages and session lifecycle. The session sync/domain owner projects changed messages; selected detail asks for history and timeline rows; Markdown workers parse/project/highlight; DOM commit displays visible rows. Reverse demand begins at the active viewport and visible tail and should propagate an explicit render-interest/priority signal through timeline row selection to markdown jobs. Background consumers should not trigger history hydration to produce row scalars.

Keep the existing two workers initially, but make each worker a single scheduler owner for parse/project/highlight rather than three independent CPU queues. Jobs carry key, latest generation, estimated bytes, and class (`visible-tail`, visible-history, hidden/detail, background). Reserve bounded service for the visible tail; cancel/supersede stale generations before dispatch; preserve per-key order only where tokenizer/parser state requires it. Separate long synchronous parse/highlight work into cooperative chunks or a genuinely isolated worker lane when measurement shows it can block control/visible work. A worker scheduler cannot preempt a synchronous call already executing, so bounded admission alone is insufficient. Renderer commits should be frame-paced and bounded by elapsed work; hidden components should retain source/state as appropriate while suspending optional parse/highlight/DOM updates, then reconcile from latest state on reveal. Required session execution must not follow this presentation visibility signal.

For timeline cost, preserve current virtualizer and stable row identity. First instrument array sizes and projection time for a delta versus a full list replacement. If every stream update reconstructs whole-list maps, move toward an incremental producer-owned ordered message index/change set, so one changed message updates its turn/rows without scanning every loaded message. History hydration stays reserved for the explicitly opened session/detail and bounded pages; telemetry/sidebar consumers use domain projections.

## Actual-trigger validation gates

The ledger correctly says no idle-startup or unit-only closure. Run this in the real Electron renderer + sidecar with 1, 3, and 6+ simultaneously working sessions, including long histories and code-heavy streaming. Record trace/build fingerprint and test a visible selected session while other sessions stream in hidden tabs and while same-affinity markdown keys occupy both lanes.

- Hold a large parse/highlight on each worker, then stream one short visible-tail fragment. Measure provider-event-to-DOM-commit p50/p95, worker dispatch wait by job kind/lane, stale-job count, parse/highlight compute, long tasks/frames, and ensure visible content advances by a bounded frame/deadline even when a provider pauses after one fragment.
- Switch away from and back to a mounted/retained session tab. Hidden sessions continue provider/tool/persistence lifecycle, while optional parse/highlight and DOM commits for hidden content fall to zero or an explicitly bounded cadence; reveal converges to latest content without another session activation or history refetch.
- Exercise 1/3/6+ working sessions with visible and offscreen sidebar rows. Count animations, animation frames, row attribute/character mutations, and Layerize/compositor time. `DenseWorkingIndicator` should keep repeated-row animation cost proportional to onscreen rows and must not regress to SVG-per-row animations; a shared clock must not write tooltip attributes for closed/offscreen rows.
- Append one token at a time to long history. Track timeline projection input rows and CPU, row keys/replacements, hydrated bytes, and mounted DOM count. Negative invariant: no per-row/per-tick history hydration, no N-per-session stream fanout, and stable unaffected rows; no repeated whole-history parse for an append-only visible tail unless grammar requires a reset.
- Verify cancellation/teardown while parse/highlight work is queued: old epochs never commit after newer text, disposal releases worker-side key/cache state, and subsequent visible work is admitted without waiting for obsolete backlog.

## Evidence boundaries

Confirmed historically: September 28 compositor saturation from dense animated SVG spinner fan-out (12 animated rectangles per spinner, 24 per session across two sidebar copies); offscreen clock-driven text/attribute writes; context-panel periodic remount/history reconstruction at that capture. The historical report states the provider-specific reconstruction was later removed, but this audit did not independently verify that change or establish runtime closure. Current source confirms the single-element dense indicator and two-lane markdown worker architecture, plus timeline virtualization and stable projection mechanisms. It does not contain a current active-stream Electron trace proving bounded worker wait, hidden-tab quiescence, paced visible commit, or update cost under 6+ sessions. These remain risks and acceptance gates, not current confirmed failures.
