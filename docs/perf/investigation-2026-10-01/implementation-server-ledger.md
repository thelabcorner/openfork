Status: **agent catalog ownership and live detail-read projection implemented; provider-list ownership remains open**. This is implementation evidence, not a performance closeout. No app/server restart or runtime latency measurement was performed.

## Agent catalog: producer to consumer

The retained local V1 consumer is `loadAgentsQuery` in `packages/app/src/context/global-sync/bootstrap.ts:419-438`. V1 now calls `legacy.app.agents({ directory })`; the protocol client has no ambient directory (`packages/app/src/utils/server.ts:95-123`), so this explicit query is required. The V1 generated operation accepts `directory` and `workspace` (`packages/sdk/js/src/v2/gen/sdk.gen.ts:954-979`). It no longer prefers `/api/agent` on V1. Current-protocol servers continue using the current location-scoped endpoint.

The producer is the shared Core `AgentV2` state plus its authoritative built-in and workspace-configuration transforms. `packages/core/src/agent/catalog.ts:32-71` constructs a narrow location node from `AgentV2.node`, `Config.node`, `FSUtil.node`, `Global.node`, and `Location.node`; it runs `AgentPlugin` followed by `ConfigAgentPlugin` in the same order used by `PluginInternal`. It does not instantiate `PluginInternal`, tools, indexes/watchers, PTY, session runner, snapshots, or the full `locationServices` graph (`packages/core/src/location-services.ts:45-100`). The separate subpath avoids eagerly importing plugin/config dependencies into every `@opencode-ai/core/agent` consumer and avoids a self-reexport cycle.

The V1 transport is declared separately in `packages/opencode/src/server/routes/instance/httpapi/groups/agent-catalog.ts:8-25`, with `WorkspaceRoutingMiddleware` but no `InstanceContextMiddleware`. Its handler (`handlers/agent-catalog.ts:11-51`) obtains the middleware-resolved explicit location, fetches the location catalog context from `AgentCatalog.MapService`, and projects current agent facts into the retained V1 `Agent.Info` contract. The route assembly is separate from `RootHttpApi` in `server.ts:256-260`; it receives auth, workspace routing, schema errors, and the catalog map at the application boundary. This keeps unrelated root-route harnesses from acquiring catalog services.

The reverse demand path is the V1 startup query. It asks for the resolved choices associated with the already-known directory; it no longer induces `/api/agent` and the broad current location graph. Missing directory is rejected by workspace routing instead of falling back to `process.cwd()`.

## Active V1 content detail projection

The durable source remains the PartTable. `Session.updatePartDelta` publishes `MessageV2.Event.PartDelta` without writing each fragment; the producer (`packages/opencode/src/session/processor.ts`) retains the authoritative mutable text/reasoning part until the final `session.updatePart` resolves. The new process-local `packages/core/src/session/current-parts.ts` registry borrows a snapshot closure to that part, keyed by session/message/part and protected by a generation token. It stores no duplicate content buffer; entry count is proportional to admitted active producers and open reasoning parts. Snapshots are detached clones and only requested message IDs are visited.

The overlay is applied only at `packages/opencode/src/server/routes/instance/httpapi/handlers/session-read.ts` after explicit detail/all/page history hydration. It does not alter `MessageV2.page`, provider history, export semantics, or durable storage. A detached overlay replaces an empty durable row or contributes a part just before its first durable row appears. `CurrentParts.node` is explicitly included in the served route graph (`server/routes/instance/httpapi/server.ts`) because a processor-node dependency alone does not provide the service to HTTP handlers.

PartDelta now carries an optional producer-authored UTF-16 code-unit offset. The app reducer appends legacy unversioned events as before; for offset events it accepts contiguous coverage, deduplicates matching overlap, and rejects gaps/conflicting overlap. The active session content owner (`packages/app/src/context/server-session.ts`) turns rejected/missing-part offset events into the existing session-local history repair path. The generic global reducer also understands offsets, but the production `server-sync.tsx` call sites explicitly set `sessionContent: false`; active content reduction is owned by `server-session`.

Release follows durable finalization: text/reasoning part update then token-matched release, with `Effect.ensuring(...releaseAllLiveParts)` as the teardown barrier for failure, retry, and interruption. No explicit global cap is applied: an arbitrary entry cap would reject already admitted model output. The owner is bounded by active producers/open parts, so this memory cost scales with active work and disappears on finalization/cleanup.

Evidence: `bun test test/server/httpapi-session.test.ts -t 'detail recovery'` passed and proves an active producer prefix is returned by the real HTTP detail route while durable history remains unchanged. Core registry, overlay, and app offset helper tests passed (1, 3, and 4 tests); `packages/app bun run typecheck` and `packages/opencode bun run typecheck` passed. The helper tests cover detached ownership, stale-token protection, empty durable-row repair, no-op history semantics, replay/overlap/gap/conflict, and UTF-16 offsets. These prove the mechanism and lifecycle wiring, not full Electron loss recovery or latency under concurrent active sessions.

## Provider list: historical open item — desktop startup boundary superseded

The two paragraphs immediately below record the pre-split state and are retained as historical evidence. They are **not** the current desktop startup path. The standalone `ProviderCatalogApi` described later in this ledger is now the V1 `provider.list` operation used by app/bootstrap provider reads; it has Authorization/workspace-routing ownership without `InstanceContextMiddleware` or `InstanceStore`, and it returns cached/config/auth/env baseline data plus revisioned runtime/account contributions. Runtime `Provider.list()` remains an explicit full-materialization operation for legacy/non-startup consumers. A later cold-test investigation also showed the recurring ~7 second first provider-test cost is shared test/runtime graph construction rather than a production `Provider.list()`-specific measurement.

The startup provider request remains behind `InstanceContextMiddleware`: `groups/provider.ts:39-91` places `GET /provider`, auth-method lookup, and OAuth actions in one group. Its handler's `list` at `handlers/provider.ts:40-78` composes config filtering, `ModelsDev`, `Provider.list()`, auth state, and a T3 account-model projection. `Provider.list()` at `packages/opencode/src/provider/provider.ts:2986-2988` calls `currentState()`, which calls `InstanceState.get` and can invalidate/rebuild it at lines 2978-2984. Provider initialization itself depends on config/auth/env, plugin, ModelsDev, runtime flags, credentials, credential resolution, route/health services, and HTTP client (node dependencies at `provider.ts:4283-4303`). State construction awaits arbitrary `plugin.list()`, plugin provider model callbacks, plugin auth loaders, custom provider hooks, and model discovery callbacks (`provider.ts:2620-2630`, `provider.ts:2720-2790`, `provider.ts:2840-2875`). `ModelsDev.get()` also populates from a cache/network if absent (`packages/core/src/models-dev.ts:195-276`). These are observable source dependencies; no individual stage has been measured as the 101-second blocker.

Do not fix this by removing middleware from the mixed group while leaving handler dependencies unchanged, or by exposing only `ModelsDev` as the provider list. That would either keep runtime acquisition or drop configured/authenticated/plugin/materialized providers and connected/default semantics. The stable baseline contribution is ModelsDev metadata plus explicit workspace provider config, allow/deny filters, env/auth credential presence, and built-in model/default transforms. Plugin-provided model sets, plugin config-hook mutations, arbitrary custom provider discovery, and T3 account-model projection have no current independently materialized catalog contract. The correct next boundary is a Tier-2 baseline owner plus a revisioned plugin/catalog contribution snapshot; plugin discovery must not be awaited by the startup read, while the existing runtime `Provider.Service` remains the execution/model-resolution owner. Do not claim full parity until tests prove `all`, `default`, `connected`, and T3 compatibility behavior against that contribution boundary. Provider startup remains unresolved in this change.

### Progressive Tier-2 provider catalog implementation (in progress)

Added a standalone `GET /provider` `ProviderCatalogApi` group with Authorization middleware only (`packages/opencode/src/server/routes/instance/httpapi/groups/provider-catalog.ts:12-30`, mounted at `server.ts:267,548`). The route calls `ProviderCatalog.Service.list({directory?, config})`; omitted directory is a deliberate global request and explicit directories must be absolute. Explicit reads resolve the project worktree and read global plus location-scoped V1 server config files directly; they do not construct an `InstanceStore` or call `Provider.Service.currentState` (`handlers/provider-catalog.ts:26-55`). The catalog combines `ModelsDev.getCached()`, V1 provider config/enable-disable filters, env/auth presence, and exact-location runtime contributions. A cold ModelsDev fetch is detached and emits `provider.catalog.updated`; runtime contributions publish the same event with monotonically increasing per-location revision (`provider/catalog.ts:32-120`, `provider/catalog-contributions.ts`).

The public result carries `catalog.status` (`pending|partial|ready`) and `revision`. The cached/config/auth/env baseline is `partial`; `pending` means no baseline is available yet. `ready` requires the location's runtime provider contribution and, when the explicit T3 compatibility profile is active, a current account-model projection. This avoids waiting for runtime discovery or remote account configuration on Tier-2 reads. The contribution registry snapshots `Provider.currentState.providers` after that state is built; custom model/config-hook parity remains dependent on an actual runtime contribution. It is process-local and disappears on restart, so a fresh process correctly begins at the baseline status.

### Provider catalog and execution follow-up (October 2)

The SDK route is now present in the canonical `OpenCodeHttpApi` graph (root-owned regeneration); the distinct group retains operation identifier `provider.list`. The route handler provides `ProviderCatalog.node` and the durable `Database.node` directly, with Authorization middleware only. It does not acquire `Workspace.Service`, `InstanceContextMiddleware`, or `InstanceStore`. Directory queries require absolute paths and read shared plus explicit-location V1 config. Workspace queries now resolve the durable `WorkspaceTable` row by ID; they use its stored directory, reject a missing directory, and reject a supplied directory that resolves differently. This avoids silently treating an unresolved workspace request as global. The workspace projection is deliberately limited to rows with a stored local directory; remote/unmaterialized workspaces return BadRequest pending a location-aware remote catalog contract.

The catalog uses `fromConfigProvider` shared with runtime state construction, preserving configured model aliases, API URL/NPM selection, capabilities, costs, limits, and variants. Its baseline derives `all`, `default`, and `connected` from cached ModelsDev, V1 config enable/disable filters, process environment names, and global auth credential IDs. `Env.Service` is excluded because it is Instance-scoped; per-location runtime env overlays are reflected only by the later runtime contribution. Runtime contributions are secret-redacted and publish `provider.catalog.updated` with location and revision. In the explicit T3 compatibility profile, the catalog now also fingerprints stored OpenCode credentials and the effective V1 provider filters, then starts one detached account-capability projection using the shared Console credential resolver and the same `consoleModel` / `consoleProviderInfo` transforms as V1 execution (`catalog.ts:100-176, 210-267`; `provider.ts:2183-2350`). It merges those rows through `projectT3CodeAccountModels`, preserving T3 account aliases, connected providers, and enabled/disabled filtering. The first read does not wait for remote account configuration; it remains `partial` until that projection is available. Account rows are process-local with a five-minute TTL and refresh on credential/config fingerprint change or a later read; concurrency is bounded to two location refreshes and four accounts per refresh. The catalog publishes revision events to known directories when a refresh completes. A credential mutation does not itself eagerly refresh the catalog; stale snapshots can persist until the next catalog read, and the five-minute TTL is a fallback. The projection contains only public model/provider capability data, not the account secret. No direct integration test yet verifies a T3 account response with a mocked Console account endpoint, so this establishes implementation parity by reuse of the execution transforms plus existing pure T3 projection tests, not end-to-end account-fetch proof. Runtime contribution and account projection must both be ready before status becomes `ready`.

The runtime provider implementation now defers each `discoverModels()` callback until `Provider.getModel()` selects that provider, with per-provider promise coalescing and catalog contribution publication after discovery. This removes the cross-provider discovery loop from state construction, but does not establish first-prompt independence from unrelated provider initialization: `currentState()` still awaits ModelsDev `get()`, `plugin.list()`, configuration hooks, and provider/auth/model initialization before `getModel()` is reached. No selected-fast-provider / blocked-unrelated-provider execution test has passed. First-prompt lazy initialization remains open; no broad `ready` claim is made.
