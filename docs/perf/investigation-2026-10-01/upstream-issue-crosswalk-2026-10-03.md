# Upstream performance issue crosswalk

Started October 3, updated October 4, 2026. This is a differential audit of upstream OpenCode reports against the current OpenFork source and the running Electron test gates. Upstream issue text is a lead, not evidence about OpenFork. The compatibility boundary in the repository guide remains authoritative.

## Findings

| [#6310 — LSP workspace diagnostics bloat persisted tool results](https://github.com/anomalyco/opencode/issues/6310) | OpenFork's write and patch tools queried the full per-client LSP diagnostic maps after edits and embedded the full workspace map in durable tool metadata. The edit commit path had already scoped metadata to the edited file, but neither its projection nor write/patch metadata bounded diagnostic counts or opaque LSP fields. | **Direct mechanism confirmed and fixed at the LSP/tool producer boundary.** `LSP.diagnosticsFor(files)` reads only selected document entries from each client rather than rebuilding every workspace map. Write/edit/patch metadata then stores changed-file findings only, at most 20 per file / 100 total / 64 KiB aggregate; long messages are clipped and `relatedInformation`/opaque `data` are dropped. Focused projection, write, edit, and patch tests pass 92 tests / 250 assertions. Package typecheck reports no diagnostics in changed LSP/tool files, but remains red on existing unrelated dirty-tree compatibility/ACP/TUI type errors. |
| [#32511 — FFF scans and content-indexes the entire home directory](https://github.com/anomalyco/opencode/issues/32511) | The report's source explicitly sets `enableFsRootScanning: true` and `enableHomeDirScanning: true`, while OpenFork's pinned `@ff-labs/fff-bun@0.9.4` defaults both flags to false. OpenFork passes the explicit workspace `location.directory`, `disableContentIndexing: true`, and does not enable either wider scan. | **Reported whole-home/root scan and content-index mechanism absent in current OpenFork source.** A user who explicitly chooses their home directory as the workspace can still ask the project-scoped scanner to enumerate that root; this report does not establish a cross-workspace/home scan. Watcher duplication and cross-project native resource pressure remain separate evidence gaps. |

A dedicated Swarm workload and resource envelope would be needed before changing its separate task/member domain. |
| [#30166 — session roots hidden until the project path query resolves](https://github.com/anomalyco/opencode/issues/30166) | The upstream report described a boot race where sessions arrived before `path.directory`, causing directory-filtered root sessions to disappear. OpenFork's per-directory child store initializes `path.directory` from the explicit directory key while the path query is pending, and the session-list query is keyed by that same normalized directory. The full-app replay gate exposed a separate OpenFork ownership leak: notification handling treated the global SSE event sentinel as a workspace and called `ensureDirSyncContext("global")` to read session title/parent metadata. | **The upstream empty-path race is absent; the separate sentinel leak is fixed at the notification consumer.** Notifications now resolve only server-owned Session metadata (background priority), use its authoritative workspace directory, and do not bootstrap a workspace or hydrate message history to decorate notifications. A production Electron 1/3/6+ run after a controlled sidecar restart proves zero `global` workspace children, zero Tier 2/3 requests with `global`, zero renderer/console errors, one history repair, visible prompt/tail, and a reopened SSE. Preserve the negative invariant at this notification boundary. |

Existing per-directory startup and session-list tests cover these source invariants; project-switch Electron behavior remains part of the broader gate. |

No keyed full-message or legacy part reads occurred; the composer remained usable and renderer/console errors were zero. This is structural and boundedness evidence, not a universal latency threshold. The source fingerprint was `eb710806054417bada33a3ca3739fa9caa9d60aa1694d70d91df7ad33bca25ff`; click-to-detail measured 3.481 seconds and the fixture insert 4.391 seconds, both diagnostic only. Current Protocol JSON aggregate decode still materializes full stored content before its projection; that transitional surface needs an independently justified storage/decode change only if a retained OpenFork product surface uses it.

The source audit found two independent unbounded detail transports: V1 `PartTable` hydration and current Protocol embedded `content[]`. V1 now pages a bounded part subset in one indexed query; current Protocol list reads crop count/bytes before the HTTP response. Both attach compact omission metadata that the app carries into the timeline as a visible recovery row. Full execution/history reads remain unchanged. The current Protocol database value is still one JSON aggregate, so SQLite/Drizzle materializes and Core decodes the full content before the list projection runs. Large or truncated messages cannot take the one-shot recovery route, preventing the renderer blow-up, and bounded V1 progressive detail paging is now available from the recovery row, while current Protocol still lacks an equivalent pager. The remaining current-Protocol decode/detail costs keep #28844 partially open; the real 80k Electron open gate is now complete.
