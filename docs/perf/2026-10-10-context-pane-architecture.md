# OpenFork Context inspection: performance and architecture (2026-10-10)

## Scope and ownership

- UI: `packages/app/src/components/session/session-context-tab.tsx`
- V1 production transcript source: `message` / `part` tables, V1 compaction state machine in `packages/opencode/src/session/message-v2.ts`.
- Context overlays: `session_context_state` and durable `SessionContext.ContextOpsApplied`, not arbitrary component-local state.
- Server: `packages/opencode/src/server/routes/instance/httpapi/handlers/session-context.ts`.
- Context inspection domain owner: `packages/opencode/src/session/context/inspection.ts`.
- Usage/occupancy analytics are a **different**, scalar-only source (`Usage.sessionContext`). Do not hydrate conversation history merely to produce the overview.
- Current/V2 special-agent transcripts retain their distinct host-owned read-only ledger path.

## Changes implemented and verified

1. **Targeted mutation validation**: `MessageV2.probeContextTargets` reads only selected V1 message metadata, signature presence where necessary, and exact part ownership from one deferred WAL snapshot. It deduplicates IDs and uses 128-ID SQL batches, avoiding materialization of massive tool outputs in JS. `applyOps` rejects missing or foreign-session targets, part IDs belonging to another message, authoritative STATE mutations, and signed-reasoning edits/exclusions before publishing a durable event. The policy is centralized in `canApplyContextOperationFacts`, with equivalence tests against hydrated validation.
2. **Effective-history page cutoff**: `MessageV2.streamCompacted` shares the *same* state machine as `filterCompacted`; it stops fetching pages once a completed compaction (or its retained-tail start) establishes the canonical oldest effective boundary. A deferred read transaction holds the same consistent WAL snapshot across every cursor page and its part hydration. The unfiltered `stream()` path is unchanged for callers that truly need full history.
3. **Dedicated WAL reader and coherent snapshots**: Context's history loader uses `readDb` instead of the global SQLite writer connection. The domain `ContextInspection.read` collects effective V1 history, parts and overlay flags in **one deferred read transaction**; `ContextInspection.ledger` and `ContextInspection.preview` derive their results from the same immutable returned rows. In-memory tests continue aliasing the primary connection.
4. **Accurate preview**: `projectContextPreview` uses the compiler's actual effective/excluded message sets; pinned exclusions remain effective, transformed text/tool output is re-estimated, genuinely empty output stays zero, and the excluded token count covers only actually removed messages. It reuses original ledger estimates for unchanged message references. Compiler errors now surface instead of being silently reported as no-op context.
5. **Earlier optimization work**: client-side ledger request coalescing, lazy mounting of the 200-row inspector, bounded previews, independent live-telemetry overlays, SQLite compact-usage summary/cache prechecking and LRU reuse. These were implemented in the preexisting dirty worktree and are not solely attributable to this round.
6. **Bounded API admission**: The Context-operations HTTP schema rejects batches exceeding 256 operations before any SQL probe or durable event. Restore/include and pin operations skip signature scans entirely. The admission probe returns only role and provenance scalars, not full message JSON.
7. **No implicit execution Instance on Context**: removed `InstanceContextMiddleware` from the Context group, while retaining workspace routing and HTTP authorization. Context handler existence/special-agent admission now reads just `session.metadata` instead of calling full `Session.get`. The global workspace router now prefers `Session.getRoutingLocation`, which reads exactly `directory` and `workspace_id` without deserializing permissions, metadata, model, or summary diffs. Existing mocks retain a backwards-compatible fallback to `get`.
8. **Linear-time, low-allocation ledger and preview projection**: `SessionLedger.buildWithRows` derives preview/type/token/signature/edit-target facts in one part traversal per message and counts *effectively* excluded/edited records (pinned wins, signed reasoning cannot be excluded, invalid host STATE overlays ignored). `projectContextPreview` merges compiler outputs and the ordered ledger with constant auxiliary memory rather than building two history-sized maps; mismatched or duplicate compiled history is rejected rather than reported as plausible occupancy.
9. **Adaptive WAL lane isolation for Context inspection**: `ContextInspection.read` examines no more than three 50-message pages on the interactive `readDb` lane. If it cannot prove the effective compaction boundary, it rolls back the bounded transaction and replays the *entire history and overlay read* on the lazy independent `scanDb` connection. Never merges snapshots or publishes a truncated ledger. Deeply compacted histories retain the single-reader fast path, and uncompacted history cannot hold the interactive read admission permit beyond the bounded probe (although synchronous native SQLite still uses JavaScript CPU time unless the optional async reader-worker lane is enabled).
10. **No-op mutation admission checks, opaque-reference safety**: `probeContextTargets` also projects narrow part type/status facts and whether the message has editable text/reasoning, with no transfer of large tool outputs to JavaScript. `canApplyContextOperationTargetFacts` rejects text replacement targeting the wrong part kind or messages without editable content, and tool collapse targeting a non-tool or unfinished tool. If a V1 part has been externalized to an OPCL `$cdbRef` and therefore cannot prove its signature/type inline, the admission probe **fails closed for exclusion and text replacement**; never interprets absent inline metadata as unsigned reasoning. Restorative operations retain compatibility with old overlays.
11. **Bounded UTF-8 event writes**: `withinContextPayloadBudget` rejects any replacement larger than **4 MiB** and any operation batch with more than **8 MiB combined replacement text**, *before* SQLite queries. It measures real UTF-8 byte counts, not potentially misleading JavaScript UTF-16 string length. The batch-count schema still caps operations at 256; historical EventV2 replay schema was intentionally not tightened.
12. **Read-only audit/fork routing**: `SessionContextState.getOpsHistory` and `getForkOrigin` now use the dedicated query-only `readDb`, not the primary EventV2 writer handle. This avoids contention with event projection but does **not** bound a huge legacy operation-history response; keyset pagination and a separate bulk read lane remain future architecture.
13. **Atomic Context mutation admission**: Core EventV2 now accepts an optional `PublishOptions.admit(seq)` writer-transaction callback executed **before** projectors, operational `commit`, event-sequence advancement, and durable insert; a refused admission rolls back the entire transaction and never notifies listeners. `MessageV2.probeContextTargetsFrom(input, writerDb)` shares exactly the previous signature, semantic ownership, and part-target policies; the Context HTTP handler calls it through `SessionContextState.applyOps({ admit })`, with session existence and special-agent identity rechecked under that writer lock. The separate WAL inspector remains for read-only usage but no longer authorizes a later write. Cross-process writes participating in the same SQLite WAL serialization cannot change a targeted message/part between this admission and its event projector.
14. **Bounded keyset ledger endpoint**: `GET /session/:sessionID/context/ledger/page?limit=50&cursor=...` returns at most 50 actionable entries, `hasMore`, `nextCursor`, and the history mode. Ordinary V1 sessions hydrate **only** selected message+part pages and overlay rows within one WAL snapshot. Compacted sessions use the existing canonical compiler-ordered fallback to preserve retained-tail semantics (the fallback still hydrates entire effective history); V2 special-agent ledgers keep the separate read-only legacy path. The legacy `/context/ledger` and preview endpoints remain unchanged. The cursor is session-bound and fenced with the durable aggregate event sequence; edits, part updates and compaction invalidate stale page cursors. No historical snapshot is falsely promised across requests.
15. **Schema-owned compaction and opaque-reference probes**: three new indexed predicates avoid historical O(N) metadata scans and preserve fail-closed behavior when older OPCL content hides whether a message/part is a compaction marker: `message_session_summary_probe_idx`, `message_session_opaque_probe_idx`, and `part_session_opaque_context_probe_idx`. The migration generator produced new migrations `20261010070439_context-ledger-summary-probe`, `20261010070619_context-ledger-opaque-probe`, and `20261010071242_context-ledger-opaque-part-probe`. `bun run migration --check` succeeded after generation. Initializing a new database or applying migrations to an existing one creates the indexes through the usual process; this work does **not** migrate the user's live running database, and no runtime was restarted.
16. **Narrow message header projection**: the ordinary V1 `pageContextFactsOn` path now reads only message ID, session, role, creation time, and provenance using scalar SQLite projections. It never transfers unneeded arbitrary message/provider metadata into JavaScript when bounded producer-written part facts are available. Existing canonical V1 hydration still owns legacy v0 fallback, and tests check parity on authoritative host STATE and unstamped legacy-shell semantics even with 2 MiB of irrelevant message metadata. On a disposable 50-message × 128 KiB metadata fixture (9 alternating samples), full header hydration median **8.384 ms**, scalar projection **3.782 ms** (**2.22×** isolated), complete facts-backed page **4.246 ms**. Neither result establishes typical Context latency gains for small real message headers.
17. **Chunked UI ledger paging**: `createSessionContextLedgerPager` now retains stable page chunks and accumulates loaded-only token/exclude/pin/edit counts incrementally. It no longer clones the entire seen-ID Set or copies every previously loaded entry when adding one 50-row page; a flattened compatibility view is lazily computed only when requested. The V2 pane renders nested stable Solid `<For>` page chunks and mounts a full loaded-row lookup only when the user opens raw transcript inspection. A synthetic 20,000-row/400-page CPU benchmark, comparing earlier clones+full-totals+lookup rebuild against chunked incremental accumulation, measured **409.035 ms** versus **2.141 ms** (**191×** *for just that repeated-update algorithm*). Neither figure includes network, DOM node construction, Solid scheduling, or Electron responsiveness. The client still mounts every manually loaded row; true virtualization and server-owned all-history totals remain open.
    - A separate small-header control (50 messages × 1 KiB metadata) measured full header hydration **0.390 ms** vs narrow scalar projection **0.461 ms** (**~18% slower** in that isolated run). Scalar extraction has a small fixed cost for ordinary compact messages, traded for much lower transfer/allocation when metadata is large. These figures should be tested against real message-size distributions before treating the header projection as a universal Pareto improvement.

## Reproducible synthetic benchmark

Run from `packages/opencode`:

```sh
bun script/benchmark-context-history.ts 5000
```

It creates a temporary database with 5,000 obsolete V1 messages, 15 retained-tail messages, one compaction, one summary, and one subsequent user message; it compares `filterCompacted(stream(sessionID))` against `streamCompacted(sessionID)`. Equality of all projected messages is asserted before timing. Five alternating repetitions are measured and the median reported.

Observed sample (2026-10-10):

| Measure | Original | Compaction-aware |
| --- | ---: | ---: |
| Median history read | 95.622 ms | 0.877 ms |
| Effective messages returned | 18 | 18 |
| Isolated speedup | — | **109.08×** |

**Limits:** This synthetic workload intentionally represents a heavily compacted transcript and thin old message bodies. It is not a production p95, overall Context page speedup, no-compaction speedup, or concurrent-session benchmark. Additional warm-cache, payload-size, and SQLite contention effects can shift results. The benchmark owns only a disposable temporary database; it never starts/restarts the sidecar.

The same benchmark also supports `bun script/benchmark-context-history.ts 5000 --no-compaction`: a sample returned 5,018 effective messages, original median **109.005 ms**, optimized median **96.333 ms** (**1.13×**); this shows no severe regression on a non-compacted case in that isolated sample, not a universal throughput guarantee.

An updated file-backed run (after adaptive routing, with the lazy scan connection warmed) compares the original full-history reader, compaction-aware reader, and complete Context inspection (including overlay read):

| History fixture (5,018 stored) | Original | Compaction-aware | Adaptive inspection |
| --- | ---: | ---: | ---: |
| Compacted to 18 effective | 59.899 ms | 0.522 ms | **0.545 ms** |
| All 5,018 effective (no compaction) | 66.164 ms | 53.713 ms | **58.772 ms** |

The adaptive path is intentionally **not** a large uncompacted-history speed breakthrough; it isolates the expensive read queue. The 3-page limit is a bounded latency design parameter, not a proof of ≤3-page CPU work for pathological huge parts. Cold scan connection creation is excluded from these warm medians and should be evaluated separately.

Additional synthetic admission benchmark from `bun script/benchmark-context-admission.ts 4` (4 MiB stored tool-output part; seven alternating repetitions):

| Admission read | Median | Relative to hydrated single message |
| --- | ---: | ---: |
| Full V1 message+part hydrate | 9.931 ms | Baseline |
| Pin/include metadata-only probe | 0.621 ms | **15.99× faster** |
| Exclude/edit signature-aware JSON probe | 10.165 ms | **0.98×** (not faster) |

The signed-reasoning guard must inspect part JSON to avoid false negatives; it is not a speedup on one large tool payload, but does avoid transferring that payload into JavaScript. Indexing a durable signed-reasoning metadata bit at the producer is required to eliminate that remaining cold-path scan without weakening the guard. These numbers vary between executions and reflect no production concurrent load.

Route projection from `bun script/benchmark-session-route-projection.ts 4` (21 alternating samples, synthetic 4 MiB Session metadata): full Session read **6.9102 ms** median versus two-scalar routing **0.3850 ms** (**17.95×** isolated). This is not whole-route latency, and ordinary short metadata yields a smaller benefit.

CPU-only ledger projection from `bun script/benchmark-context-ledger.ts 10000` (10,000 messages × 5 parts): former multi-pass median **2.790 ms** versus fused median **2.399 ms** (**1.16×** in that sample); semantic normalization, not raw throughput, is the larger benefit.

CPU-only preview from `bun script/benchmark-context-preview.ts 50000` (50,000 ordered messages, 11 alternating samples): hash-map median **22.272 ms** versus ordered merge **1.657 ms** (**13.44×**); the new algorithm allocates zero history-sized maps rather than two. This assumes the enforced compiler ordered-partition contract.

New keyset-page experiment, `bun script/benchmark-context-history.ts 5000 --no-compaction`: with 5,018 synthetic durable V1 rows, an early unindexed version of the page had a roughly **54 ms** first-page median because it scanned every historical message for summary status. An indexed local comparison, with a corrected fixture that does not falsely set `summary:true` for uncompacted sessions, yielded **1.000 ms** first-page median against **60.662 ms** full-history baseline. A contemporary unindexed corrected run measured **4.236 ms** for the page and **55.259 ms** for the full baseline. These are *different fixture/run conditions*, not a rigorously paired deployment speedup; the improved shape requires the generated summary probe index. Once the API also reads page revision fences and performs opaque-message/part probes, rebenchmark the full finalized path. Extreme single-part sizes, cold migrations, IO saturation, and concurrent real sessions remain unmeasured.

**Post-migration finalized-path measurements**, now with all three tracked indexes, opaque-message/part safety probes and durable-event revision fences enabled (5 warm/alternating samples, disposable databases, 5,018 stored messages):

| History | Full-history reader median | First ledger page median | Relative |
| --- | ---: | ---: | ---: |
| Uncompacted, 5,018 effective | 67.414 ms | **1.608 ms** | **41.9×** isolated |
| Compacted, 18 effective | 76.382 ms | **2.179 ms** | **35.1×** isolated |

This compares different response sizes, and the page returns no global totals; it is therefore **not** a 41.9× whole-Context pane speedup or full API parity claim. The compacted first page intentionally uses canonical effective-history reconstruction. For giant tool parts, both page time and JS allocation may remain high until producer-owned ledger scalars exist.

**Writer-cost warning (not yet certified Pareto):** `bun script/benchmark-context-probe-index.ts 5000` uses five in-memory SQL microbenchmark rounds with 5,000 message+part pairs and 512-character part payloads. All three partial predicate indexes increased median insert time from **20.718 ms to 29.577 ms** (**+42.8%, 1.77 µs more per pair**) while reducing aggregate no-hit probe time from **6.035 ms** to ~**0.002 ms**. With 500 pairs and 65,536-character parts, median writer time grew from **22.743 ms to 37.190 ms** (**+63.5%, 28.9 µs per large pair**); most of this case's cost came from the partial expression index on `part.data`. These are *isolated SQLite measurements*, not production event throughput, renderer p95 or WAL contention. The three probes are justified by fast fail-closed historical checks, but the cost is a measurable **writer-path regression** until a producer-materialized, cheap-scalar substitute and real concurrent-session benchmarks establish a better Pareto point. Do **not** claim regression-free performance closure.

## Remaining frontier: truly unbounded uncompacted transcripts

### 2026-10-10 03:30 CT — further direct implementation

- **Producer-fact full-history totals:** new `packages/opencode/src/session/context/totals.ts` computes canonical chronological `messageCount`, included/excluded token estimates, `excludedCount`, `pinnedCount`, and `editedCount` using *only* durable v1 per-part scalar flags, with one SQL aggregate and no JS message-body hydration. A shared source-policy list is derived from the canonical turn-provenance registry to preserve host STATE protection. v0/incomplete/OPCL parts, opaque message headers, and compaction boundaries fail closed to **unavailable**, never zero.
- **Independent totals endpoint and revision fence:** `GET /session/:sessionID/context/ledger/totals` runs on the lazy dedicated WAL `scanDb` connection in a deferred transaction with EventV2's durable `event_sequence.seq`. `ledger/page` includes its own `revision`. The UI launches the totals request after receiving the first page, but accepts it only when session identity, local generation and durable revision all match. A late response or nonmatching external writer revision cannot overwrite the currently loaded rows. Full totals are independent of loaded-only counts. This is **read-time O(history)**, *not yet incremental O(1)*.
- **Important rejected design:** initial implementation awaited `readChronologicalTotals` on the *first-page request*. A measured 5,018-row synthetic case regressed to **13.221 ms median**. This was removed: keep page latency independent from O(history) aggregate work. With totals in a separate read, an updated disposable SQLite benchmark measured original full history **121.434 ms**, first 50 ledger entries **2.885 ms**, and independent full-history totals **18.913 ms** median for 5,018 uncompacted messages. The aggregate requires only a fixed-size response but still competes for server CPU on a synchronous native reader.
- **Real viewport virtualization:** `ContextLedgerVirtualRows` in `packages/app/src/components/session/session-context-virtual-ledger.tsx` uses the existing TanStack Solid Virtual and stable `messageID` keys. A pure prefix-offset/binary-search index resolves each viewport row in **O(log loadedPages)** without flattening the entire ledger. Offscreen components unmount. Two tests check 19,963 indexed rows spread across 400 pages and irregular empty pages. Visual/keyboard accessibility and actual Electron frame-time tracing remain unverified.
- **Lazy-getter performance regression repaired:** an async totals update initially used `{...latest}`, which eagerly invoked the intentional `entries` getter and flattened all rows. It now explicitly preserves a lazy getter. A focused test asserts the getter remains an accessor after asynchronous totals settle. Deferred/stale totals races, A-B-A navigation, and foreign revision rejection are separately tested.
- **Bounded legacy repair (explicit only):** `backfillLegacyContextFacts({sessionID,limit<=100,after?})` transactionally upgrades validated inline historical V1 parts to the same producer-owned `context_* v1` scalar representation. It accepts a keyset cursor, skips corrupt and opaque `$cdbRef` rows, and never runs automatically on Context activation or claims those skipped records are zero-token. A focused test proves a v0 part invalidates totals, explicit repair restores exact equality to the full canonical ledger, and an unresolved OPCL ref keeps totals unavailable. This is not yet a background/writer-fair automatic backfill service.
- **Verified OPCL scalar compatibility:** after the original V1 producer emits full `context_* v1` flags, OPCL can compress the physical `part.data` JSON without invalidating the producer-written tokens/kind/preview/signature facts. The page and totals paths now accept **opaque physical parts with complete v1 facts**, while still rejecting opaque parts with missing v0 facts and opaque *message headers* whose role/provenance cannot be proven. A disposable regression rewrites a valid v1 part to an unresolved physical `$cdbRef`, preserves the scalar fields, and verifies that page rows and all-history totals remain byte-for-byte equivalent to their pre-externalization values.
- **Writer-fair repair hardening:** the explicit `backfillLegacyContextFacts` worker now discovers historical parts, validates schemas and resolves OPCL refs using the canonical `EventV2.resolveProjectionRef` decoder **outside** the primary SQLite writer transaction, using the WAL reader. It then performs only bounded, short SQL updates using compare-and-swap on `part.id`, `session_id`, original `data`, and `context_projection_version=0`; a concurrent producer modification wins, with `skippedConflict` reported. Decoded refs retain `context_opaque=true` but gain verified v1 facts. Dangling refs, disabled OPCL, malformed part kinds and payloads remain safely unprojected. No automatic writer-competing backfill loop is launched. The new ref-aware conversion path relies on the separately tested canonical EventV2 resolver; a full end-to-end historical OPCL-ref repair fixture remains a certification gap.
- **Read-contention probe:** `bun script/benchmark-context-concurrency.ts` builds its own disposable SQLite DB with 100 synthetic sessions × 20 messages. After warming all sessions, it measures 25, 50, and 100 simultaneous page+totals requests twice in forward/reverse order; the completed sample yielded p95 medians **1.40 / 1.40 / 5.00 ms**, with throughput medians **834 / 788 / 485 requests/sec** respectively. Each response was validated against its session. These numbers measure **synthetic reads only**, not 25/50/100 genuinely generating sessions, first-token latency, SQLite writer contention during tools, Electron frame drops or production p95. They do expose tail growth under heavy synchronous read fanout. Each benchmark owns a disposable temp DB; none touches or restarts the live daemon.

### Remaining architecture

### 2026-10-10 11:30 CT — transactionally incremented totals Pareto assessment and safe hot-read closeout

- **Canonical delta kernel, implementation + randomized oracle:** new Core module `packages/core/src/session/context-incremental-model.ts` defines a pure per-message contributor derived only from validated v1 part scalars, state ownership and overlay flags; `contextMaterializedDelta(before,after)` plus checked `addContextMaterializedTotals` implement reversible inserts, updates, deletes and idempotent replay. The comprehensive test `packages/opencode/src/session/context/incremental-model.test.ts` passed **10,000 randomized differential comparisons** to `SessionLedger.buildWithRows` (text, reasoning signatures, file/tool status, pins, edits, host STATE) plus **9,000 update/delete/replay operations**, underflow/opaque/compaction negative cases: 3 tests, 10,112 expectations. This is a candidate semantic foundation, **not an activated persistent projection**. It never lies about opaque/v0/compacted histories.
- **Naive transactional materialization rejected on write cost:** disposable `bun script/benchmark-context-durable-ledger.ts` creates 3,000 messages and runs 15,000 deterministic part/overlay edits against a baseline and an extra per-message ledger-row + per-session summary-row design, with updates transactionally derived from affected part facts. Exact row-sum reconciliation, deletes, duplicate replay and rollback succeed, but three trials measured **2.40–3.08× insertion cost and 4.38–5.33× mutation cost**. The prototype delivers O(1) reads at the price of enormous write amplification, so **do not enable it, add indexes/triggers, or add a Core schema migration yet**. This measurement is a small isolated Bun SQLite in-memory microbenchmark, not production inference throughput; a true writer-path benchmark remains required before any activation.
- **Production-safe bounded hot-read memo (enabled):** `packages/opencode/src/session/context/totals-cache.ts` and `totals.ts` use the persistent query-only `scanDb` connection and accept cached six-scalar totals only if both **EventV2's session event sequence and SQLite `PRAGMA data_version`** match the committed read snapshot. `data_version` invalidates writes from primary or other SQLite connections even when they were made directly by SQL outside EventV2. The cache is per-handle via WeakMap, LRU-bounded to **128 sessions per scan connection**, has no timers, caches safe `undefined` for unsupported records, and is **disabled for `:memory:`**, where scanDb aliases the writer and SQLite data_version cannot detect own-connection writes. Cold reads still compute the exact canonical SQL aggregate with v0/OPCL/STATE/compaction protections. The cache adds **zero transactional writes** to active streaming.
- **File-backed correctness evidence:** the new `totals-wal.test.ts` opens a disposable, migrated file-backed SQLite database, verifies a real persistent scan connection's increasing `data_version` after raw primary writes without EventV2, and proves zero stale totals across a token change, message insertion, v1→v0 invalidation and v0→v1 recovery. Each cached response is a shallow six-scalar copy so mutating one caller's result cannot poison another caller's totals; the WAL fixture tests this isolation explicitly. Pure tests in `totals-cache.test.ts` cover event revision mismatches, SQLite version mismatches, cross-database handle isolation, cached absence, LRU recency/eviction and invalid capacity. The 3 cache tests plus 1 file-backed test and 3 fuzz/delta tests **all pass**.

The read cache is not an incremental materialized ledger: changes anywhere in the SQLite file conservatively invalidate it, even unrelated sessions' commits. A 25/50/100-session **active-writer** workload may therefore have a much lower hit rate than this warm benchmark. It is also a process-lifetime cache, so process restart incurs a cold aggregate before it warms again.

**Decision:** the absolute requirement is *fast context insight without penalizing model/tool generation*. The previous conceptual milestone of mandatory synchronous per-event materialization is **rejected in its naive form** after direct measurement. Prefer the now-proven exact version-fenced warm-cache path for real usage. Revisit a truly durable O(1) snapshot only with a **turn-settlement/revision CAS design**, or a producer-owned O(1) delta fast path proven not to increase p95/99 writer latency, replay drift or WAL contention under actual multi-agent traffic. Do not conflate warm O(1) with cold O(1) or claim full durable materialization is complete.

The page transport is bounded in **hydrated message count** for ordinary V1 sessions, and visible DOM rows are now virtualized. The per-part scalar source is producer-written, but the per-message actionable rows and all-history totals are **still read-time projections**. The old full ledger and prospective Context preview can still inspect all effective history, and a single page with jumbo legacy parts may still be expensive. The major outstanding migration is an independently versioned, durable producer-owned **per-message ledger with incrementally maintained O(1) session counters**, including source-owned delta maintenance when parts/messages/overlays/compaction change:

1. Define an independently versioned, schema-owned `session_context_ledger` projection, sourced from durable message, part, compaction and context-overlay events; reconcile V1/current transcripts with explicit provenance and generation ownership. Do not put content copies or reconstructed permission state into it.
2. Materialize bounded preview strings, token-estimation revisions, signature locks and exact current overlay flags transactionally at authoritative producers. Retain a rebuild/backfill path for old or out-of-band modified databases; track the effective compaction cutoff and invalidation watermark explicitly.
3. Replace the now-shipping O(history) totals aggregate with producer-updated, version-fenced O(1) counters only after proving delta correctness across message/part update, delete, signature changes, overlay operations, compaction and replay. Retain current bounded page and separate totals endpoint plus legacy clients as compatibility surfaces. Add a no-Pareto-regression writer throughput gate; added JSON indexes previously increased write cost substantially.
4. Extend monotonic replay/version-fence certification (now enforced for ordinary producer events and atomic Context edits) with interrupted writers, multi-process SQL changes outside EventV2, OPCL reconstruction, schema upgrades, multi-worktree restores and current-only special-agent histories. Never treat the event watermark as a fence against raw, out-of-band SQL changes.
5. Benchmark 25/50/100 **genuinely executing** sessions: p50/p95/p99 Context open latency, GPU/renderer frame delay, first-token latency, SQLite WAL time/locks, memory growth, network bytes and cancellation. Record `0` implicit Instance loads and `0` metric-only history hydrations.
6. Do not discard or overwrite unrelated dirty worktree changes; do not restart the live Electron app/sidecar.

Atomic writer admission, bounded paginated transport, independent producer-fact totals, **revision-fenced O(1) warm-cache hits**, viewport virtualization, and explicit bounded writer-fair OPCL-aware repair now exist with focused tests. **Not complete:** full materialized per-message rows, safely incrementally written O(1) *cold* totals, automatic scheduled backfill, complete end-to-end historical OPCL repair, and real active 25/50/100-session Electron/sidecar certification. The new pure delta kernel and disposable materialization benchmark are research artifacts, deliberately not activated on production writers.
