## Runtime contract and upstream reference

OpenFork's mature V1 runtime uses `session/llm.ts` and the AI SDK by default. The installed `@ai-sdk/openai-compatible@2.0.41` reads stream deltas from `reasoning_content` and `reasoning` but not `reasoning_text`. The OpenFork-owned native `@opencode-ai/llm` OpenAI Chat protocol now reads the three fields and prefers one in each event, without concatenating duplicated aliases. Upstream OpenCode's `packages/ai/src/protocols/openai-chat.ts` was used as a behavioral reference for field selection and round-trip reasoning history. The fork-specific provider/auth/tool contracts remain authoritative.

The native model carries explicit interleaved field metadata into the wire compiler and emits the corresponding field on previous assistant turns. It also accepts retained V1 `providerOptions.openaiCompatible` history. Only hosted OpenCode-compatible models that *declare* the otherwise unsupported `reasoning_text` spelling are automatically selected for native transport. If that required transport is unavailable, dispatch fails explicitly instead of silently discarding content. All other models retain their existing runtime-selection policy.

## Presentation and persistence rules

The exact unavailable notice (including its observed protocol suffix) is presentation-suppressed in shared Session UI and current timeline projection. While a reasoning block is unfinished, only a bounded prefix of that exact notice is temporarily hidden to avoid flicker. Once content diverges from the known prefix, it becomes visible; a genuine completed short phrase remains visible. Ordinary assistant text is unaffected. Durable reasoning is not modified, and same-model signed/provider continuation data remains untouched. Cross-model conversion does not inject the pure unavailable notice as assistant prose.

Reasoning-token counts, model variants, and provider capabilities cannot be used to reconstruct unavailable reasoning. Generic `<|start|>` stripping of arbitrary content would be unsafe and is deliberately not implemented.

## Follow-on stream-completion stability hardening (same day)

A second independent hazard was reproduced in native `@opencode-ai/llm`: `LLMClient.generate()` rejected a naturally exhausted provider stream without a terminal `finish`, but a raw `LLMClient.stream()` consumer could drain partial text or tool arguments without an error. The V1 Session processor is a streaming consumer. Shared `packages/llm/src/route/client.ts` now rejects natural EOF unless the stream reported either the successful `finish` or an explicit `provider-error`. The latter is an existing intentional event contract: provider rejections remain visible under their original error code/message, rather than being overwritten with a generic synthetic EOF. This is validated across seven native protocol test files (187 passed, 0 failed), including Anthropic, Bedrock, Gemini, OpenAI Responses, OpenAI Chat, OpenRouter, and OpenAI-compatible variants. An earlier over-strict iteration that required `finish` alone broke 14 provider-error fixtures; those regressions drove the corrected terminal-disposition rule.

A second V1 admission fence in `packages/opencode/src/session/llm/terminal-stream.ts` enforces the same post-normalization rule for both its default AI SDK path and native streams. It treats deliberate consumer cancellation, explicitly aborted attempts, and existing upstream errors separately; it never creates missing tool-call completions. Its state is per-subscription, and the dedicated tests exercise 1, 3, and 6 concurrent subscriptions, early EOF with and without partial output, and successful and error terminal streams. Runtime changes preserve the concurrently introduced `abortableProviderIterable` cancellation behavior.

The V1 physical retry classifier (`packages/opencode/src/session/retry.ts`) additionally treats the exact `Provider stream ended without a terminal finish event` failure as **terminal** even if a higher-level adapter labels it retryable or wraps it in a 502. Upstream may already have committed tool calls, so replaying the same physical request is unsafe; recovery, where applicable, is a separately owned turn. Ordinary transient 502/network failures preserve the original retry behavior. The focused `session/retry.test.ts` suite passed, including explicit tests of both sides of this distinction. The V1 terminal guard has 10 passing tests, including a completed tool-calling step without an overall `finish` and 1/3/6 concurrent attempts. The native protocol matrix has 187 passing tests across seven providers; no provider-error regression remains.

This is a local source/test result, not a deployed provider-specific fix. The earlier measured five-minute timeout incidents may still originate in the gateway, network, SDK decoder, or host-load/backpressure and remain subject to the independent clocks investigation in `docs/perf/provider-idle-timeout-2026-10-15.md`.

## October 15 continuation: actual AI SDK cancellation and synthetic-finish regressions

The terminal stream guard's first 10 focused tests exercised Effect streams directly. A stronger integration test combined the exact production composition `Stream.fromAsyncIterable(abortableProviderIterable(...))` with the guard. **Before the fix it failed**: Effect called `AsyncIterator.return()` even after `next()` naturally resolved `done: true`; the wrapper aborted its shared transport controller, causing the terminal guard to mistake premature EOF for host cancellation. A second test proved that an otherwise fully successful stream also acquired an unnecessary transport abort.

`packages/opencode/src/session/llm/abortable-provider-iterable.ts` now tracks natural iterator exhaustion from `next()` and does not abort or request further upstream teardown for that state. Early consumer exit still aborts before calling SDK `return()`, with bounded cleanup. The regression matrix also executes 1/3/6 simultaneous real asynchronous iterators, mixing genuine completion, incomplete EOF, and user-side early cancellation. The adapter/terminal suites passed **18/18**, then **20/20** after adding model-finish coverage.

A second live-host fixture reproduces a distinct failure when OpenAI-compatible Chat SSE transmits a normal `[DONE]` frame **without any model `finish_reason`**: the installed AI SDK emitted a synthetic successful terminal pair anyway, bypassing an EOF-only guard. By contrast, a connection closed *without* `[DONE]` already raises the SDK's more specific `OpenAI-compatible SSE ended before [DONE]` error. The fix is a conditional invariant at the V1 AI SDK normalization owner: for models using `@ai-sdk/openai-compatible`, `finish-step` with an unrecognized normalized reason now fails before producing a terminal success event. The general adapter behavior of other providers remains unchanged. This deliberately does not infer completion from token counts, text, tool activity, or transport end markers.

`packages/opencode/src/session/retry.ts` also excludes this exact missing/unrecognized reason from same-route physical retries, even under misleading 5xx/retryable wrapping, preventing accidental replay of potentially executed tools. Unit tests cover the strict/non-strict adapter distinction and recognized `stop` success; the actual V1 mock HTTP provider test passed after the change. The strict adapter also requires at least one completed model step before accepting a synthesized overall `finish` event: `[DONE]` alone, even with a `stop`-labeled overall finish, is not model-completion evidence. That distinct failure is likewise terminal to physical retries. These fixtures validate exact protocol mechanics, **not** that deployed OpenCode Go models always supply compliant finish reasons. A protocol-specific upstream wire sample and real desktop-run evidence remain open release gates.
