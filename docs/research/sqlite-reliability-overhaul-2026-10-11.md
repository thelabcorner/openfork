# OpenFork SQLite Reliability Overhaul — 2026-10-11

## Scope and evidence

This change targets the **recurrent native SQLite permit starvation** behind OXP control delays, not SQLite's storage engine itself. Existing forensic fingerprints were `c2b111a6` (long FTS), `0bbba6a9` (interactive reader), and `e3be8ca2` (`Usage.ZenFree.snapshot`). These historical fingerprints identify query *shapes*, not verified exact past SQL. The OXP in-memory diagnostics retained an additional `activity_recording/link` `EffectDrizzleQueryError` with no root SQLite code; its cause is **not established**.

Source inspection revealed:
- Single native semaphore per connection, long synchronous SQLite C calls cannot be stopped by cancelling an Effect fiber, and worker-thread termination is not a reliable native SQL timeout.
- Even with separate read and scan lanes, a lone analytics worker can still hold a permit for seconds/minutes and queue many unrelated tools.
- Bun's primary file-backed SQLite and interactive reader previously defaulted to synchronous operations on the main JS event loop.
- OXP and Memory had caller paths that bypassed pooled admission.
- Bun `--compile` executables relaunch their embedded main when invoked with `-e` unless `BUN_BE_BUN=1`; source-mode Bun tests miss this release packaging failure.

## Changes implemented / verified in the protected shared worktree

- `packages/core/src/database/sqlite-scan-process.ts` (new): a disposable, hard-deadline **read-only** SQL subprocess. `SIGKILL` on query timeout or actual Effect cancellation stops the OS process even if `sqlite3_step` never returns. Query failure is explicit (`SQLITE_SCAN_DEADLINE` or `SQLITE_SCAN_CANCELLED`), never reported as success. The same client lazily opens a new read-only connection for subsequent reads. Parent disconnect triggers child termination; the Node subprocess uses SQLite's parser-level authorizer, and Bun uses a constrained lexical admission guard plus the native read-only handle (Bun 1.4.3's authorizer-denial callback can hang). Writable/primary/control transactions NEVER enter the killable driver.
- The child runs with the owner's runtime binary, not a hard dependency on an installed system Node, and sets `BUN_BE_BUN=1` for a compiled Bun executable. Bun's legacy JSON child IPC uses explicitly tagged BigInt/Uint8Array encoding; Node V8 advanced IPC preserves native integers and blobs without this wrapper. V8 heap budget is 256 MiB (not a total OS RSS cap). Parent PID liveness is checked from a separate child worker so a blocked C statement cannot retain a WAL read lock after a parent crash.
- `packages/core/src/database/sqlite.node.ts`, `sqlite.bun-worker.ts`, `sqlite-worker-client.ts`: integrate the killable subprocess into **read-only** `scan`, `scan-pool`, and `interactive` lanes for Node and Bun. Native writer operations still wait for acknowledgments and preserve transactional outcomes. `Effect.onInterrupt` cancels only expendable reads.
- `packages/core/src/database/database.ts`: default analytical pool capacity now 2, explicitly configurable 1–4. File-backed interactive reads default to asynchronous adapters; file-backed Bun primary writes also default to existing acknowledgment-preserving async workers to eliminate main-loop `sqlite3_step` stalls, with diagnostic opt-outs `OPENFORK_SQLITE_ASYNC_READ_WORKER=0` and `OPENFORK_SQLITE_ASYNC_PRIMARY=0`. In-memory databases retain their original single-handle behavior.
- `packages/core/src/database/scan-read-pool.ts`: 3-second timeout applies strictly to **waiting for a reader lease**. It does not truncate the callback. Timed-out/cancelled queued requests cannot release another fiber's permit. The actual SQL subprocess deadline defaults to 10 seconds per statement; users get a bounded explicit error instead of waiting indefinitely.
- `packages/opencode/src/oxp/session.ts`, `exchange/memory.ts`, `exchange/memory-read-runtime.ts`, Core `session/inspection.ts` (earlier turn): OXP searches and Memory recalls use leased read-only analytics connections instead of the primary/interactive connection; the service's policy still validates root authority before returning search results.
- The `ZenFree` query-shape rewrite, cache singleflight, and indexed provider model lookup were *concurrently developed in the shared worktree by another contributor*. Preserved, never overwritten.

## Required before declaring the incident resolved

1. **Build and activate** a new candidate backend. The connected OXP status reports `runtime.refreshable=false` for this tool host, so the running sidecar was intentionally NOT restarted or changed. Working-tree source and isolated tests are not live-release proof.
2. **Real representative dataset:** collect p50/p95/p99 for primary, interactive, scan, scan-pool, control and OXP activities during 25–100 concurrent agent Sessions. Validate no 30s permit timeouts, no stuck cancellations, steady-memory bounds, and no corruption.
3. **Packaged release matrix:** the standalone Bun test covers the Windows compiled CLI behavior. Also test Electron/Node sidecar packaging and supported macOS/Linux artifacts; preserve the proper spawn mode under Electron.
4. **Remaining write-side contention:** OXP `activity_recording/link` once raised an `EffectDrizzleQueryError`, but the sanitized diagnostic cannot establish SQLite cause (BUSY, schema, transient file IO, etc.). Do not claim it is fixed merely because reads are isolated.
5. **Performance/overheads:** quantify CPU, memory and throughput of default two subprocess readers and asynchronous Bun primary compared to the existing defaults. If large legitimate analytical queries exceed 10s, they now explicitly fail; pagination and indexes should resolve such cases rather than restoring unbounded execution.
6. **Portability + security:** independently certify packaged Bun, Electron, Node versions; test attacker-controlled CTE/PRAGMA inputs in sandbox, and prevent attached secondary databases. Hard-kill is restricted to natively readonly handles and must NEVER be used on a writer or unresolved COMMIT.

**Disposition:** concrete working-tree implementation and host-free regression evidence, **not** a claim that the recurring live SQLite issue is fully closed. Preserve shared dirty/concurrent changes; follow exact ownership rules before any release integration.

## Further findings from final hardening

- A new adversarial sandbox fixture demonstrated that Bun 1.4.3's `node:sqlite` emulation can **hang until the 3s query deadline** when its `setAuthorizer` callback returns `SQLITE_DENY` for a hidden `WITH … INSERT`. This is not an acceptable security guard on Bun: the scanner process now installs SQLite's parser-level authorizer on Node only; **Bun additionally enforces a quote/comment-aware lexical DML/ATTACH guard** before child IPC, on top of its native `readOnly: true` connection. This remains a deliberate cross-runtime limitation: the small lexical filter is defense in depth for trusted internal SQL, not a full SQL parser for untrusted arbitrary queries.
- A Windows disposal regression was exposed: `child.signalCode` can become non-null when `kill()` is *requested*, before the file handle has actually closed. `SqliteScanProcessClient.close()` now coalesces concurrent closes and waits for the subprocess's real `exit` event (with a 5-second failure deadline), instead of returning early and causing a subsequent Windows `EBUSY` removal/swap failure.
- A dedicated sandbox test `sqlite-scan-authorizer-20261011.test.ts` proves hidden DML and EXPLAIN ATTACH are rejected, a quoted `UPDATE` string and commented DELETE are not misclassified, external target file is never created, and the original DB rows remain unchanged. **1/1 PASS, 5 assertions** after the cross-runtime correction. An earlier red attempt took 3 seconds and exposed the Bun callback incompatibility; it was not promoted as a passing behavior.
- Bun's *default primary writer* has also been moved to its existing worker-backed adapter, opt-out via `OPENFORK_SQLITE_ASYNC_PRIMARY=0` for controlled diagnostic benchmarking. This prevents even an unexpected writer-side native SELECT or busy lock wait from freezing the OXP control JS loop. The accompanying default-primary worker regression passed; other Bun transaction isolation and concurrent-writer regressions passed. This does **not** make a blocked SQLite WAL writer individually killable; writer transaction outcomes remain acknowledgment-preserving.
- New `scan-read-pool.ts` regression proves a queued request fails in 75ms under a deliberately pinned lease, releases none of another owner's permits, and a subsequent request reuses the reader correctly.
- Broad final test pass: **31/31 Core** DB tests across 14 files (174 assertions), **21/21 OpenFork** OXP/Exchange/Zen usage tests across five files (144 assertions), plus focused primary-worker and adversarial authorizer tests. Core typecheck passed after these changes. The native **Node and Bun** SQLite adapters have both been exercised with their actual Effect SQL layer.
- Desktop OXP refresh remains unavailable in this tool host. Nothing has yet been deployed against the active user database or observed across 100 real concurrent Sessions.

## Second hardening iteration — subprocess reaping, quota and packaged Electron

This iteration addressed further provable defects without activating the live sidecar.

1. **RED→GREEN Windows handle lifecycle:** A new 8-iteration stress fixture `sqlite-scan-process-exit-barrier-20261011.test.ts` reliably failed before the change with `EBUSY` deleting a disposable SQLite database after timeout/recovery/close. Cause: the old deadline path cleared `this.child` before the previous OS process had truly exited. `SqliteScanProcessClient` now tracks every subprocess generation as a pending process-close barrier, even generations retired by timeout or cancellation, and `close()` waits for all generations. 8/8 sequences with 24 assertions pass, including native Windows file removal.
2. **Cross-lane concurrency:** `sqlite-cross-lane-stress-20261011.test.ts` exercised 48 concurrent primary writes, 24 control reads, 12 analytical scans with a disposable file-backed WAL database and validated exactly 48 durable rows with expected sum 2352. Passed; representative run 272.2 ms, repeat 145–168 ms (test-specific, not production 100-session p99).
3. **Read-only administrative safety:** Constrained `PRAGMA` admission to actual connection initialization commands and read-only schema introspection; reject WAL checkpoint, journal-mode mutation, disabling query_only, outsized cache and lock timeout changes, and multi-statement injection. The first expanded integration test exposed that a legitimate `PRAGMA query_only` read must remain legal; repaired the allowlist and confirmed all five related suites GREEN (8/8, 78 assertions).
4. **Release runtime:** The actual Desktop Electron 42.3.3 executable was used for a Node-mode smoke test. A probe removed inherited `ELECTRON_RUN_AS_NODE` before constructing the scanner, proving subprocess spawning sets the flag itself. `ELECTRON_SCAN_SUBPROCESS_OK electron=42.3.3` exited 0. The generated smoke bundle was deleted.
5. **IPC failure cleanup:** IPC arguments are serialized **before** registering a job/deadline; serialization failure cannot leave a ghost pending query. Synchronous/asynchronous IPC sends failing now terminate their owned subprocess after rejecting the request. `sqlite-scan-ipc-error-recovery-20261011.test.ts` passed: cyclic malformed bind rejected, zero pending jobs, subsequent valid read, close and native Windows file unlink all succeeded.
6. **Measured warm IPC overhead, synthetic:** `bench-sqlite-reader-ipc-20261011.ts` (200 post-warmup SELECTs/variant) measured Bun worker p50/p95/p99 **0.048 / 0.096 / 0.130 ms** versus killable isolated Bun subprocess **0.070 / 0.139 / 0.356 ms** (means 0.054 and 0.090 ms). CPU/platform/load dependent; excludes real SQL scans and retention overhead. No claim of production speedup here.
7. **Existing broad suites:** OXP ActivityRecorder, Diagnostics, Sqlite: **30/30 PASS**, 270 assertions; Core OxpActivity plus BUSY_SNAPSHOT tests: **20/20 PASS**, 108 assertions. These do not explain the production `EffectDrizzleQueryError` link failures, which remain an open evidence gap.
8. **Safety:** no live user SQLite DB edits, live sidecar restart, Git staging/commit/reset/clean, or modification of other contributors' untracked OXP diagnostics code. Test data created under disposable OS temp folders, own generated smoke bundles removed.
