# SQLite primary-permit contention — forensic ledger (2026-10-10)

## Observed failure
At 2026-10-11 00:18–00:19 UTC, the Desktop log showed a primary SQLite connection permit held by a native SELECT for at least 49,031 ms. The old diagnostic recorded query hash c2b111a6 and SQL length 1,065, with workerStage=executing. A runtime_owner heartbeat upsert then timed out waiting for the same permit after 30 seconds, and swarm retirement reported a secondary reconciliation failure. Vite CSS hot reload also happened but is not proven causal.

Expanded source-log inspection found repeats of **the exact same primary fingerprint beyond 325,000 ms** (run 2b0a9cd9), plus an independently slow **interactive** SELECT of hash 0bbba6a9 and length 1,001 beyond 46,000 ms (run 113923de). Both read lanes can monopolize their own single-connection permits. This is stronger evidence of a recurring expensive query family than the original excerpt alone; it still does not establish what SQL ran.

A hash and length cannot reliably reconstruct arbitrary SQL. The historical diagnostic intentionally retained no SQL text or bind values; the original statement is **not yet identified**.

## Read-only production data inspection
openfork-dev.db contained approximately 7.05 GB (WAL, 8192-byte pages), including event 731,817 rows, part 449,450 rows, usage_record 216,511 rows, message 121,710 rows, session_message 14,291 rows, swarm_task_run 1,541 rows, and swarm_task_lease 179 rows. The sqlite_stat1 planner-statistics table was absent.

The lack of index statistics can impair plan selection; it does not establish the source of this specific 49-second SELECT. The principal compiled Usage-summary queries and 4,541 generated single-table SELECT variants did not match the original 32-bit fingerprint/length. No live user database writes were performed during inspection.

## Repairs
1. RuntimeOwner ensureRow and heartbeat use a lazily initialized, reusable, worker-backed control-plane write connection. It has a short native busy timeout with bounded application-level retries. Primary foreground reads can no longer starve heartbeat permit acquisition. In-memory handles retain one shared store.
2. Swarm retirement hazard inspections use the query-only interactive reader instead of the primary.
3. Every successful raw SessionExecutionOwner.tryAcquire now registers its exact process-wide live generation. Previously this happened only in tryAcquireLocal. Retirement incorrectly inferred that raw-acquired sessions were orphaned and reclaimed a still-running generation; forensic instrumentation reproduced a returned recovery state of recovered for a live owner. Exact activation tracking and disposal/retention cleanup fix this path.
4. Planner maintenance uses a separate native worker under a DB-local cross-process lock, zero native busy wait, and a startup grace period of ten seconds, then runs approximately daily. Failures (including cross-process locking) retry on a bounded exponential schedule of 1–30 minutes rather than waiting an entire day. SQLite versions 3.46+ may execute PRAGMA optimize=0x10002 with bounded ANALYZE; older versions are skipped and memory databases excluded.
5. Contention and slow-query reports (duration >= two seconds, per-fingerprint cooldown) now include privacy-safe SQL structure data: whitelisted internal table names, join/predicate counts, grouping and ordering flags, fingerprint, connection lane, and elapsed duration. They never record raw SQL, parameter values, external identifiers, or call stacks.
6. The Node and Bun native workers recognize only the two measured historical SQL hash/length pairs. On first matching execution per worker, before executing the suspect query they run EXPLAIN QUERY PLAN with the same bindings and emit a **sanitized plan vector** (full scans, indexed seeks, temporary B-tree sorts, covering/index usage, plan steps, and status). This can capture the execution plan even if the main query subsequently blocks for minutes. The worker does not transmit plan details, SQL, bind values or user identifiers over IPC. Diagnostic failures cannot abort ordinary SQL.
7. **End-to-end control-plane isolation:** prior work separated RuntimeOwner heartbeats but left SessionExecutionOwner tryAcquire, release, releaseIfDrained, tryClaimRecovery, complete/abandon recovery, and requestInterrupt on the primary lane, with runtime/ownership snapshots on the interactive reader. Thus a >325-second primary SELECT still prevented stop/cancel/handoff after the heartbeat mitigation. These bounded, exact-generation, indexed reads and IMMEDIATE CAS transactions now share the independent, worker-backed control-plane connection. Startup-only bulk reconciliation remains on its original lane to avoid blocking high-priority control traffic with scans. WAL still serializes actual writers; this does not bypass a long exclusive writer transaction.
8. **Workload-specific read isolation, corrected against prior throughput data:** file-backed heavy analytical `scanDb` now always uses an asynchronous native worker; file-backed interactive `readDb` remains opt-in asynchronous via `OPENFORK_SQLITE_ASYNC_READ_WORKER=1` or `layerFromPath(filename, { asyncReadWorker: true })`. Both always open their native handles `readonly:true, readwrite:false, create:false`. This selection explicitly preserves the documented 100-Session throughput regression of the global read-worker experiment (17.76/s synchronous versus 12.49/s read-worker), rather than promoting the entire hot path because one slow-query event-loop benchmark looked favorable. Node backend already runs SQLite on native workers. Native read-only protection is independently tested by attempting writes after turning `PRAGMA query_only` OFF.
9. **Exact operation attribution without secrets:** the client captures a restricted, namespaced Effect operation label from the current parent span and stores only that label in the active SQL permit diagnostic. The log now carries `sqlOrigin` next to `sqlShape`, length, and hash. Paths, identifiers, dynamic span labels, SQL text and trace IDs are not retained. If no qualifying static operation span exists, `sqlOrigin=unknown` is explicitly reported rather than fabricating an origin.

## Delegated-session admission and transaction contention closeout (same-day continuation)

**Selected candidate:** restore the end-to-end fake-provider admission gate and prevent ordinary concurrency from aborting unrelated Sessions on the SQLite WAL writer lock. This was prioritized over prematurely inventing the SQL text for the historical 531-second SELECT. All testing used independently generated temporary databases and local fake provider responses; the running desktop backend and the user's production DB were not restarted or modified.

### Root-cause sequence and corrected code

1. The original 5- and 100-Session harness failures were not model-selection issues. After adding terminal `snapshotMany` diagnostics to the isolated benchmark, all five workers had already transitioned to error. The initially visible failure was `GoalAutomation.requeueClaim`'s unconditional UPDATE, executed in a Session runner finalizer even when no Goal continuation had ever been claimed. An indexed, read-only ownership preflight now returns false without taking a WAL writer lock when no claim exists. Real owned claims still use the authoritative process-owner **and reservation-ID compare-and-set**; the operation retries only genuine `SQLITE_BUSY` with a five-second bound. The negative preflight is not used to authorize or transfer ownership.
2. With that redundant write eliminated, the next observed failure was `TurnCheckpoint.begin`'s unconditional stale-row UPDATE for every previously unseen Session. On a new Session no stale checkpoint exists, so it needlessly contended for the global writer slot. The code now selects a potential stale row with a bounded, indexed read first, conditionally runs the original guarded UPDATE with bounded busy retries, and adds the Session to the healed set **only after success**.
3. The next surfaced error was `session_checkpoint` INSERT on concurrent turn starts. The INSERT now retries SQLITE_BUSY for at most ten seconds using the **same immutable checkpoint ID, ordinal, timestamp and payload**. Constraint and other nonbusy errors still propagate; no tool or model operation is replayed.
4. At 25 overlapping Sessions a distinct failure remained: **two workers successfully reached the fake provider but then errored on `BEGIN IMMEDIATE` SQLITE_BUSY** (23/25 completed). Native busy_timeout was intentionally short to protect Bun's event loop, yet transaction acquisition lacked the necessary cooperative retry. Both Bun's synchronous adapter and Node's worker-backed adapter now retry **only a failed BEGIN** with bounded, jittered Effect sleeps (15-second overall deadline, 30–160 ms backoff). They retain the connection permit through retries. The gate does not admit COMMIT, ROLLBACK, SAVEPOINT, nested statements, or DML, so external side effects are never replayed to obtain a writer lock.
5. The isolated benchmark can now set `OPENFORK_BENCH_PROVIDER_ADMISSION_MS` (clamped to 1–120 seconds, default 30 seconds); if the overlap gate fails, it reports terminal worker state/activity/errors rather than misleadingly presenting a zero-provider-request result without context. No runtime configuration or production provider credentials are changed.
